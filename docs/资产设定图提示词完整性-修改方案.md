# 资产设定图提示词完整性：修改方案

状态：**已实施**（第十一节记录实施时的取舍；Demo 验收未执行）。分析基线 `0da67bc`。

> 本文合并了此前的两份草案：以「从实际发送正文里切出主体区」为主线；风格参考、基准图视觉审核两处吸收另一份草案的要求；不采用内联 `Subject:` 标签，也不建立审核记录与失效台账。

## 一、问题

Demo 的 P01 应该生成黑色越野车，实际生成的图片是银灰色皮卡。`art.json` 里 P01 的 `image.prompt` 写了黑色 SUV、亮起的车灯、哑光深色车漆、车身下沿和轮拱的红褐色泥，但实际请求里没有这些主体特征。P01–P13 的 sheet 都缺少独立的主体描述；P03 黑伞和 P04 红伞的实际请求，去掉尺寸差异后完全相同。

## 二、结论

问题不在读错字段，而在**作者契约、实际发送正文和校验责任没有闭合**。

- 只有 `image.sheet` 会发给图片模型（道具变体发送 `states[n].prompt`，n ≥ 1）。`image.prompt` 是单张展示图，不进出图计划。这一点代码、文档、自测三处一致。
- 文档要求 sheet 写入资产的身份锁（`mint-art/references/sheet-prompt.md` 第一节第 2 条），但没有任何检查要求 sheet 里有这个资产自己的描述。
- 现有检查只查固定内容：版式短语、画幅、渲染句、纯净段、尺寸档、白底。资产自己的内容一律不查。
- 唯一以资产自身描述为对象的检查（角色区分度）比较的是不发送的 `image.prompt`。

因此，一份只剩固定框架、主体描述为空的 sheet 可以通过全部检查；`image.prompt` 写得再完整，也不影响结果。

## 四、方案：从实际发送正文里切出「主体区」

不新增字段、不加标签、不提升 schemaVersion，只收紧检查。两个 skill 各自实现一份，保持自包含，不跨 skill 导入。

### 4.1 同一份正文

每个 skill 新增 `sheetTargets(doc, production, opts)`，产出 `{id, kind, role: base|variant, text}`：

- `kind` 包括场景、变体场景、道具、道具状态、人物、生物、群像。
- `text` 是**最终发送正文**。开启 `--style-ref` 时，风格匹配句已经按 4.3 的位置插入。

`imageJobsFrom` 只从这个函数取正文；全部 sheet 检查只遍历这个函数的结果；`imageJobsFrom` 输出前再对最终 `text` 执行一遍结构解析，有问题就报错，不依赖调用方事先执行 validate。validate、checkup、公开 API、图片计划因此检查的是同一份正文。

不变量：未开启风格参考时，基准任务 `job.prompt === image.sheet`，道具后续状态任务 `job.prompt === states[n].prompt`；开启时，`job.prompt` 与源正文只差插入的那一段风格匹配句。

### 4.2 确定性结构检查（代码执行，不通过就阻断）

1. **收尾**：按空行切段，最后一段在空白规整后必须**等于**纯净段，不再使用包含判断。
2. **画风段**：纯净段之前的那一段以 `Overall style:` 开头，并包含 `style.*.render` 原句。
3. **去掉固定框架**：
   - 版式句按模板起止标记识别：场景、道具从 `One <画幅>` 到 `anywhere in the image.`；人物、群像从 `Layout requirements:` 到 `The image contains no text and no logos.`。
   - 带字物品按 `sheet-prompt.md` 第五节，把「无文字」那半句换成 `the only text is …; no logos anywhere in the image.`，结束标记不变，这段文字随版式一起剥掉。
   - 道具再去掉正面光那一句；开启风格参考时，再去掉 `STYLE_REF_LINE`。
   - 剩下的部分就是**主体区**。标记按句子识别，不依赖段落位置，所以 Midjourney 写法把主体放在开头、和版式同段也能切出来。
4. **基准图**：主体区必须非空。不设字数门槛，字数不能代表内容。
5. **变体**（道具 `states[1…]`、带 `variantOf` 的场景、Midjourney 以外的人物变体写法）：主体区以 `Based on the reference image` 开头，并带 `Change only the following:`，后面至少有一个变化项。Midjourney 变体按 `model-midjourney.md` 的主体锚点写法检查，不强套通用的 keep／change 句式。正文里的 reference 字样不能代替任务依赖，参考依赖仍来自 `variantOf` 或道具基准任务。
6. **同批去重**：同类基准图的主体区在空白规整后**完全相同**就报错。完全相同是结构事实，不是相似度判断。
7. **场景光影锁原文照抄**：场景基准 sheet 必须原文包含 `lighting[0].prompt`。文档本来就要求光影锁写进 sheet，样例也是原文照抄。
   - 道具 **不** 要求 sheet 原文包含 `states[0].prompt`。基准状态说明可能带现场摆放（例如 Demo P01 写了两辆车和夜间湿坡），不能机械抄进单件白底设定图；它和主体区是否一致交给 4.4 的内容复核。
8. **变体逐任务全量检查**：`states[1…]` 同样检查画幅、渲染句、白底、尺寸档、匿名尺寸参照。按文档，变体会原样照抄这些内容。
9. **角色区分度**：Jaccard 检查从 `image.prompt` 改到 **sheet 主体区**。原先不查 sheet 的理由是「固定文本占比高」，固定文本剥掉之后这个理由不再成立。0.75 的阈值仍然只是启发式提示，报错文案说明它不代表语义审核。原有 `image.prompt` 相似度检查改名为「独立插画提示词相似度」，避免与设定图混淆。
10. **适用范围**：`designStatus: none` 的身份登记不要求设定图；planned 不进入生成计划；ready 才生成任务。缺少 production 时，独立设计仍可检查文本结构，画风和画幅明确标为 skipped；图片计划继续要求完整 production，不提供默认值。

### 4.3 风格参考

`--style-ref` 在 `images` 运行时才决定，作者编写 sheet 时并不知道是否挂参考图、哪个角色是基准，所以风格匹配句仍由代码插入，但要满足：

- 插在 `Overall style:` 段之前，单独成段，纯净段仍然收尾。
- `STYLE_REF_LINE` 作为固定框架参与解析：插入后的最终正文必须通过 4.2 全部检查，主体区不含这句，不影响去重和区分度。
- 文档同步说明：风格参考只借画风，不借基准角色的身份。

### 4.4 内容复核（大模型或人工执行，代码不判定）

在两个 skill 的 pass 文档里加入复核清单，在 `identity-inputs` 摘要里给出对照表：把最终发送正文的主体区，和 anchors、`facts`／`sourceRefs`、`image.prompt`、`states[0]`（场景为 `lighting[0]`）并排列出。

复核内容：

- 类别、颜色、材质、标记、状态是否一致。
- 每个锚点在主体区里能不能画出来。
- 同批资产依靠什么区分。
- 适配目标模型时，最终请求有没有丢弃、改写或新增未经复核的约束。

复核必须由执行 agent 在编写后另行发起一次审核调用（同一模型也可以），或由人工完成；编写时的自评和结构检查通过都不算复核。结论为需返修或待确认时，不提交生成。

中文锚点和英文正文的语义对应，以及「黑色 SUV 与银灰皮卡是否同一辆车」这类问题，只能由人或模型判断。代码不做关键词匹配，也不冒充审核；`validate` 成功文案保留「内容未评审」。

不在代码里调用大模型做自动审核：结果不确定，同一份数据可能这次通过、下次不通过；还会引入新的依赖和成本，不符合 skill 自包含、只做确定性检查的设计。

### 4.5 生成后的视觉审核（大模型或人工执行）

在两个 skill 的 `media-handoff.md` 加入：

1. 下载并核验文件后，拿实际成图逐项对照锚点、类别、颜色和版式；不能只根据文件存在、生成回执或请求文字判断合格。不一致就返修或重新生成，重新生成仍须遵守现有授权规则。
2. **基准图通过视觉审核后，才能挂成变体或风格参考的参考图。** 变体也要独立看图，确认保持项未变、指定改动确实出现。
3. 没有看图能力时，交付「已生成、待审核」的材料并明确说明，不当作可投产图片交给下游。

不新增审核记录文件、失败日志或重试统计。

### 4.6 报告

art 和 cast 的报告把「实际发送正文」（来自 `sheetTargets`）放在第一位，并高亮主体区；反向提示词紧随其后。`image.prompt` 标注为「单张展示图，不进出图计划」。角色报告不再把整个 image JSON 当作唯一提示词展示；原始 JSON 导出保持完整，不把展示默认值写回数据。报告不得把「图片已存在」写成「审核通过」。

## 五、`image.prompt` 的处理：保留，降为非权威字段

- **保留的理由**：它的语义独立成立——单机位、方向光、浅景深、不画尺寸参照。拼进 sheet 会和三格版式、正面光的规定冲突。删除它会牵动 mint-setup 的 `character.lighting`、`promptLocal`、报告和 schema 版本，超出最小修复范围。
- **代价**：它和 sheet 可能写得不一致。黄色自行车用例在本方案下仍然能通过结构检查，这一点明确交给内容复核。

### 备选方案：新增 `image.subject`

新增英文字段 `image.subject`，要求 sheet 和 `image.prompt` 都原文包含它，与 render 原句的做法相同。两个字段在结构上不可能分歧，黄色自行车用例会被拦下。代价是修改 schema（art、cast 都要提升版本）、改写全部样例，Midjourney 的 160 词上限也更紧。它只保证两个字段一致，不保证写得正确。如果团队认为字段不一致本身不可接受，再升级到这个方案。

## 六、为什么不采用内联 `Subject:` 段

1. **仍然是关键词检查。** 写一句 `Subject: an object.` 就能通过，并不比「主体区非空」更可靠。
2. **和 Midjourney 写法冲突。** `model-midjourney.md` 规定「媒介和主体放最前」，开头那句本身就带主体。另起一个带标签的段落会降低主体权重，`Subject:` 这个词还会作为 token 发给模型。
3. **变体无法适用。** `sheet-prompt.md` 第三节规定变体不重新描述要保持的内容，所以 `Subject:` 不可能成为通用规则。
4. **和角色现有结构对不上。** 角色本来就是「脸和体型 / 服装」两段，统一成一段需要改写全部样例。

主体区解析不需要标签，Midjourney 写法也能覆盖，更简单，覆盖也更全。

## 七、为什么不建立审核记录与失效台账

另一份草案提出由执行 agent 维护 `cast-handoff.md`／`art-handoff.md`，逐任务记录请求摘要、图片摘要、审核结论，并定义输入变化后的失效规则。本方案不采用：

- 这些规则都是 agent 行为，离线测试无法验证，写成契约只会制造「有记录即通过」的假象。
- 本质上是一套新的审核台账，维护成本高，与「不新增门失败累积日志或统计功能」的方向冲突。
- 现有 `assetDigest`／`sheetHash` 失效链已经覆盖了「改正文或换图后下游批准失效」。

保留下来的只有 4.4、4.5 中可以直接写进 pass 文档和 `media-handoff.md` 的行为要求。

## 十、验收与验证边界

**验收条件**

1. `node skills/mint-art/scripts/run-selftests.mjs` 与 `node skills/mint-characters/scripts/test-all.mjs` 通过；在独立复制目录分别运行两个 skill 的测试，确认不依赖兄弟 skill。
2. 第九节每一个反例得到期望结果。
