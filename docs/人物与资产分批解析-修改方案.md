# 人物与资产分批解析：修改方案

状态：**已实施**（mint-characters 4.1.0、mint-art 4.1.0；两个 skill 的自测与仓库级独立复制测试全部通过）。**第七节的串行实测尚未执行**：按用户要求先完成全部实施，dispatch 中的分批字数与 B 段门槛仍是初始经验值，实测后再校准。分析基线 `60261b5`。涉及 mint-characters 与 mint-art 两个 skill，cast 与 art 的 schemaVersion 均保持 1，不改变正式契约。两个 skill 各自实现，代码互不引用。

> 本文取代此前的两份并行方案草稿（characters、art 各一份）。那两份照搬了 [outline 分集并行解析方案](outline分集并行解析-修改方案.md) 的「并行读取 → 合并 → 串联」路线；经第一性原理和奥卡姆剃刀审查后，A 段改为**串行接力**，B 段保留并行但删去多余机制。审查结论见第三节。

## 一、要解决的问题

输入前提：一个文件夹，内含多份 md，每份一集剧本。

| 问题 | 发生在哪一段 | 最小手段 |
|---|---|---|
| 单个会话读全剧，上下文累积、压缩后丢失细节、前后集注意力不均 | A 段：身份识别 | **上下文隔离**：每个 subagent 只读一批 |
| 「读全」只能由同一会话自己声明 | A 段 | 覆盖由确定性工具检查（现有 coverage 校验已经做到） |
| 对象一多，后面对象的设计和提示词质量下降 | B 段：设计 | 每个 subagent 只设计几个对象 |
| 两个 skill 的 seed 只接受单个文件，不能直接处理分集文件夹 | 入口 | `seed --source-dir` |

前三个问题目前是**推断，没有实测**。所以本方案把一次真实长剧本的串行实测列为 A 段、B 段的实施前提（第七节）。只有入口问题是确定存在的，可以先做。

## 二、现状（基线 `60261b5`）

| 项目 | mint-characters | mint-art |
|---|---|---|
| 执行方式 | 单 agent 串行；`allowed-tools` 含 `Task`，没有派发说明 | 同左 |
| 多文档契约 | 已经支持多份 `provenance.documents[]` 与按文档的 coverage | 同左 |
| seed 入口 | 只接受一个 `--source`，固定 `D01`（`lib/identity.mjs` `seedSource`） | 只接受一个 `--source`；`--existing` 遇到新原件要求手工编辑 documents（`lib/stage.mjs` `seedFromSource`） |
| 文档 ID 约束 | `outlineErrors` 按文档 ID 和 sha256 对账 outline（`lib/identity.mjs` 106 行）；下游 script 也按文档 ID 匹配 | 同左（`validateUpstreams`） |
| ID 分配 | 首次 `reconcile` 时按 identityKey 分配 C ID；之后 registry 带指纹，直接改身份字段会使 validate 失败 | `register` 时立即分配 S/P ID（该种类最大编号加一） |
| 语义审核 | 整份一个：`review.inputHash` 等于 `reviewHash`，绑定全部身份 | 逐资产：`identityReview.inputDigest` 来自 `identity-inputs` |
| 设计写入 | 没有命令，由 agent 直接编辑 cast.json；设计块不进入身份摘要 | 没有命令，由 agent 直接编辑 art.json；设计文本不进入身份摘要 |

文档 ID 约束是本方案唯一的硬约束：分集文件夹的文档 ID 必须与 outline 一致，即 `D` 加集号。

## 三、审查结论：为什么 A 段不并行

outline 适合并行，是因为 v5 取消了身份归并，跨集依赖只剩 Q 回答等少数几项（outline 方案第三节）。人物和资产阶段正好相反，**核心任务就是跨集身份判定**：同一个人在不同集里的称呼、同名不同人、匿名声音的揭晓、同一地点、同一实物的状态链、场景变体。

并行读取把这项判定从「手里有原文的读取者」挪给「只有候选卡的归并者」，随之需要一串补救机制：

| 并行方案中的机制 | 存在的原因 | 改为串行接力后 |
|---|---|---|
| `merge` 命令、`sources.json` 核对 | 合并并行产物 | 不需要 |
| 待查清单（同名、别名重叠、名称包含） | 归并者看不到原文，需要线索 | 不需要：接力者直接对照 draft 已有条目 |
| 6 节 handoff 文件 | 读取者之间互相看不见 | 不需要：未决事项写进现有契约字段 `unknowns`、`notes`、`observations` |
| 批次前缀 `bXX~`、publish 拒绝前缀 | 批内键可能冲突 | 不需要：键从一开始就在全剧范围登记 |
| art 全局重新编号、ID 对照表 | 批内各自 register | 不需要：在共享 draft 上 register，编号天然连续 |
| `reconcile --ids-from` | 修复循环中 C ID 漂移 | 不需要：核验放在 reconcile 之前，结论引用 identityKey |
| `publish` | 防止拼接草稿冒充正式产物 | 不需要：接力草稿不是拼接产物，沿用现有「reconcile 写正式文件，再记录审核」 |
| art `validate --draft` | 并行 fragment 需要独立结构检查 | 不需要：接力中使用现有 `verify-sources`，最后执行完整 validate |

串行接力保留了上下文隔离，并且让跨集判定在原文就在眼前时完成。代价只有 A 段的墙钟时间，而墙钟时间不是本方案的目标。

B 段的情况不同：设计对象之间没有依赖，并行确实只带来好处。但原方案仍有两项多余：

- **设计文件的指纹或摘要过期检查**：B 段开始前身份已经定稿，期间除了 `apply-designs` 没有其他写者，这项检查防的是不会发生的情况。删除。
- **art 两轮设计与变体依赖检查**：按基准分组，基准场景与它的全部变体交给同一个设计者，一轮即可完成。删除。

## 四、总体流程

```
剧本目录/  第01集.md … 第12集.md（只读）
  │ ① seed --source-dir → .work/draft-00.json（文档 ID = D 加集号；coverage 为空）
  ▼
主会话分流：体量小 → 现有串行流程，在当前会话读完；体量大 → 串行接力
  ▼
② 接力者 batch-01 → batch-02 → … （一次只派一个）
  │ 输入：本批原件 + 上一份 draft（已有条目，体量小）
  │ 读本批原文；已有对象补引用，新对象新登记，揭晓时合并已有条目
  │ 输出：.work/draft-XX.json；自查通过后交回
  ▼
③ 核验者 × N（并发；按身份或资产分组）＋ 1 个漏登记核验 → .work/review/*.md
  │ 结论引用 identityKey（characters）或 S/P ID（art）
  │ 不通过：主会话修改最后一份 draft → 只复核受影响的组；两轮仍未通过就停下
  ▼
④ characters：reconcile → characters/cast.json（分配 C ID），validate，记录 review、status: identified
   art：     最后一份 draft 另存为 art/art.json，identity-inputs，逐资产写 identityReview，status: ready
  ═══════════════ 身份定稿，ID 固定 ═══════════════
  ▼
⑤ 设计者 × N（并发；每组 3–5 个对象；art 按基准分组，变体随基准）
  │ 输出：.work/designs/<ID>.json
  ▼
⑥ apply-designs：一次写回全部设计并整体校验（主会话是唯一写者）
  ▼
⑦ images → 外部生图工具；render 两份报告（与现有流程相同）
```

**写者规则：**

- 每份 `draft-XX.json` 只由一个接力者创建，之后不再修改；下一位接力者在新文件里继续。修复循环中只有主会话修改最后一份 draft。
- 核验者只写 `review/`，设计者只写 `designs/`。
- 正式文件由现有命令创建（characters 的 reconcile、art 的另存），之后只有主会话和 `apply-designs` 修改。

编号的 draft 文件同时充当接力记录：某一位接力者改坏了草稿，主会话可以从上一份重新派发，不需要额外的日志。

**阶段关系不变：** 完整流程仍然是 outline → characters → art → script → creation；art 的接力者读取正式 cast，用于 carrierRefs。

## 五、确定性工具改动

两个 skill 各自只新增两项，都只使用 Node 标准库。

### 5.1 `seed --source-dir`（两个 skill）

```bash
node {baseDir}/scripts/mint-characters.mjs seed --source-dir 剧本目录 --title 作品标题 [--budget N] [--outline outline.json] --out characters/.work/draft-00.json
node {baseDir}/scripts/mint-art.mjs seed --source-dir 剧本目录 --title 作品标题 [--outline outline.json] [--cast characters/cast.json] --out art/.work/draft-00.json
```

**文件与集号规则**（与 outline 的 `source-folder` 一致，在各自 skill 内重新实现，以保证文档 ID 对齐）：

1. 只读取目录第一层的 `*.md` 普通文件，不递归，忽略隐藏文件；符号链接解析后的实际文件不能重复。
2. 只从文件名解析集号：`第N集`（N 为阿拉伯数字或中文数字「一」到「九百九十九」）、`ep N` 或 `E N`（不区分大小写）、文件名开头的数字。解析不出或两份文件集号相同时报错，列出全部文件及解析结果。
3. 正文中匹配 `^\s*(?:#{1,6}\s*)?第(.+?)集` 的行，集号必须与文件名一致。
4. 空文件报错。
5. 文档 ID 为 `D` 加集号，补零到至少两位，也补齐到最大集号的位数。
6. 缺集不报错，在标准错误输出中列出 `missingEpisodes`。

**输出：** 与现有 seed 相同的骨架，documents 按集号排列、写绝对路径，coverage 为空，`scope: partial`。

- `--source-dir` 与 `--source` 互斥；art 中另与 `--design`、`--existing` 互斥（分批流程只用于首次生成）。
- 其他参数（`--budget`、`--outline`、`--cast`、`--lang`）的处理与现有 seed 相同；提供 `--outline` 时，文档 ID 与 outline 不一致直接报错，这正是对齐的检验。

这项改动对串行流程同样有用：分集文件夹不再需要先手工拼成一个文件。

### 5.2 `apply-designs`（两个 skill）

```bash
node {baseDir}/scripts/mint-characters.mjs apply-designs characters/cast.json characters/.work/designs/*.json
node {baseDir}/scripts/mint-art.mjs apply-designs art/art.json art/.work/designs/*.json [--production production.json]
```

**设计文件**（`.work` 中间文件，不设 schemaVersion）：一个 JSON 对象，含 `id` 和该对象的设计字段。

| skill | 允许的字段 |
|---|---|
| characters | `persona`、`voice`、`image`、`importance`、`oneLiner`，至少一项 |
| art | `designStatus`（planned 或 ready）及 `schema.md`「可选设计字段」中列出的字段 |

**规则：**

1. 文件名必须是 `<id>.json`；同一 ID 只能出现一次；`id` 必须是活动身份或资产。
2. 出现允许范围以外的字段时报错。characters 拒绝 tier 和全部身份字段；art 拒绝 facts、sourceRefs、decision、primary、variantOf 和全部身份字段。
3. 在内存中写入全部设计，执行与 validate 相同的完整检查（含 production 画风、画幅、版式与纯净画质段；production 的查找规则与 validate 相同）。**全部通过才写回**；失败时不写，按 ID 列出问题，主会话据此只退回有问题的那几份。
4. 写回采用临时文件加重命名。

设计不进入身份摘要，写回后 characters 的 `reviewHash` 和 art 的逐资产 `inputDigest` 都不变，已记录的审核仍然有效。测试要覆盖这一点。

### 5.3 不新增的命令

不新增 merge、publish、`--ids-from`、`--draft`、调度脚本或状态文件。接力过程中的自查使用现有命令：

| skill | 接力者自查 | 说明 |
|---|---|---|
| characters | `reconcile draft-XX.json > /dev/null` | 不带 `--out`，只看是否报错；借此复用 identityKey 唯一性、来源与引用越界、别名出处等检查 |
| art | `verify-sources draft-XX.json` | 检查原件摘要、引用和范围；完整 validate 在身份定稿后执行 |

## 六、角色与派发

两个 skill 各自新增 `references/dispatch.md`，内容按本节编写，互不引用。`SKILL.md` 的 `allowed-tools` 增加 `subagent`，与 mint-creation 的写法一致。不新增 agent 定义文件。

### 6.1 主会话

- 执行确定性命令，分批，依次派发接力者，并发派发核验者和设计者，向用户汇报。
- **不细读原文，不替接力者补登记。** 处理核验意见时只做定向回读。
- **分流**（初始经验值，按第七节实测校准）：原文总量约在 3 万字以内且不超过 10 集时，在当前会话串行完成；超过时接力，每批是一段连续集号，约 1 万到 1.5 万字。对白密集、人物或场景多的集，缩小批次。
- B 段：需要设计的对象较多时（门槛按第七节实测确定）并行，每组 3–5 个。
- subagent 只回报文件路径、一行状态和未决数量，不把正文贴回会话。

### 6.2 接力者（每批一个，依次派发）

**简报内容：** 本批集号、文档 ID 和文件绝对路径；上一份 draft 路径；本批输出路径；art 另给正式 cast 路径；必读文档的绝对路径：

- characters：`roster-pass.md`、`schema.md`、`source-facts.md`，以及 `dispatch.md` 的接力者一节。
- art：`schema.md`、`source-facts.md`、`lifecycle.md`、`principles.md`、`glossary.md`，以及 `dispatch.md` 的接力者一节。

**步骤：**

1. 读取上一份 draft 的已有条目（不读其他批的原文）。
2. 逐份完整阅读本批原件；长集可以先执行现有的 `chunk` 再分段阅读。
3. 对本批出现的每个人物或地点、物件：
   - **对应已有条目**（有原文证据，例如称谓、胸牌、外观、位置、物件标记）：在该条目上补 sourceRefs、别名、facts、usage 等。证据需要前文支持时，按已有条目的 sourceRefs **定向回读**前文行，不通读前文。
   - **新对象**：新登记。characters 写全剧唯一的 identityKey，不写 id；art 在当前 draft 上执行现有 `register`，ID 自然续号。
   - **不能确定是否对应已有条目**：新登记，并在 `unknowns`（characters）或 `observations`（art）中写明疑点和出处，交给核验处理。不为了减少条目而猜测同一。
4. **揭晓**：本批原文明确揭晓两个已有条目是同一对象时，合并它们（来源引用、别名、facts 取并集），notes 中写明揭晓位置和揭晓前的不知情状态。art 草稿从未发布，合并时删除被并入的资产及其 registry 条目，并改写所有指向它的 `variantOf`、`relatedScenes`、`observations[].sceneId`。
5. **art 特有**：
   - 状态变化（交接、破损、腾空、修复）写进同一道具的 facts，不新建道具。
   - 变体只在光照状态持续变化或空间状态变化（清空、破损、布置）时建立；不需要单独出图的状态写进 observations。
   - 只出现一次、暂不建资产的物件写进 observations；后续接力者发现它反复出现，可以把它提升为道具。
   - carrierRefs 只引用正式 cast 的 C ID，不按名称猜测。
6. 把本批文档的 coverage 写为 `1..lineCount`；characters 在 summary 中补写本批概要（最后一位接力者把它整理成全剧概要）。
7. 写出 `draft-XX.json`，执行 5.3 的自查，失败就自行修改，直到通过。

**禁止：** 修改上一份 draft 或任何其他文件；写设计字段；写 tier 或 budgets（characters）；确认任何审核。

### 6.3 核验者（并发）

- **按身份或资产分组，不按批次。** 同一对象的判定跨批，只看一批无法判断合并或分开是否正确。
  - characters：同名、曾被合并、带有疑点的身份分在同一组。
  - art：基准场景与其变体一组；同一 carrier 或同一状态链相关的道具一组。art 的核验材料另附 `identity-inputs` 输出的 contentReview。
- 逐个对象回读全部出处，检查：合并是否有证据、同名分开是否正确、别名和称呼是否有出处、unknowns 是否被擅自清空；art 另查变体规则、状态链顺序、decision 是否成立、carrierRefs 是否越出人物已确认的范围。
- **漏登记核验，一个**：按批抽查原件中有人物出场或发声、有具体地点、有被拿取或特写的物件，却没有被任何条目或 observations 引用的行。
- 结论写入 `review/group-XX.md`、`review/coverage.md`，每条给出 identityKey 或 S/P ID、documentId 和行号。
- 核验者只写结论，不修改 draft，也不读取接力者的自我评价。

**修复循环：** 主会话按意见修改最后一份 draft，重新自查，只复核受影响的组；漏登记有修改时同时复核 coverage。两轮仍未通过就停下，向用户报告。不新增失败累积日志。

**定稿：**

- characters：主会话为全部身份判定 tier（存在分档预算时）、检查预算，执行 `reconcile draft-XX.json --out characters/cast.json` 和 validate，写入 `review: {status:"confirmed", by, note, inputHash}` 与 `status: identified`。这与现有串行流程第三步相同。
- art：主会话判定 primary、写入预算并检查，把最后一份 draft 另存为 `art/art.json`，执行 `identity-inputs`，逐资产写入 `identityReview: {status:"confirmed", basis, inputDigest}`（basis 引用对应核验结论），`status: ready`，再执行 validate。

### 6.4 设计者（并发）

**简报内容：** 负责的 ID；正式 cast 或 art 路径；`production.json` 路径；输出目录；必读文档的绝对路径：

- characters：`profile-pass.md`、`design-schema.md`、`principles.md`、`glossary.md`、`sheet-prompt.md`、`sheet.md`、`style.md`、`realism.md`；群演另读 `crowd.md`；Midjourney 另读 `model-midjourney.md`；适用的 `genres/` 文件。
- art：场景读 `scene-pass.md`、`scene-lighting.md`，道具读 `prop-pass.md`；共同读 `principles.md`、`glossary.md`、`sheet-prompt.md`、`sheet.md`、`realism.md`；Midjourney 另读 `model-midjourney.md`；适用的 `genres/` 文件。

**分组：**

- characters：同名或外观容易混淆的身份分在同一组，便于拉开外观差异。
- art：基准场景与它的全部变体分在同一组，先写基准，再按「抄块、指向参考、保持什么、只改什么」写变体；场景的常驻道具尽量与该场景同组，便于统一材质和尺度。

**步骤：** 读取负责对象的条目，回读出处，按指南写设计，每个 ID 写一份 `designs/<ID>.json`。

**禁止：** 修改正式文件；写身份字段（characters 另禁 tier；art 另禁 facts、decision、primary、variantOf）；写负责范围以外的 ID。

### 6.5 运行环境

| 环境 | 派发方式 |
|---|---|
| Claude Code | 使用 Task/Agent 派发通用 subagent；接力者逐个派发，核验者和设计者的调用放在同一条消息里并发 |
| pi | 有子代理扩展时使用 `subagent` 工具；没有时通过 bash 启动独立的 `pi -p` 进程 |

## 七、实施前提：一次串行实测

A 段、B 段解决的问题目前都是推断。实施 dispatch 之前，先在一部真实的长剧本（建议 30 集以上）上执行一次**现有串行流程**（借助 5.1 的 `seed --source-dir`），人工记录：

- **A 段**：是否发生上下文压缩；压缩前后登记质量是否有差异；漏登记和身份误判按集序的分布（后段集是否明显更多）。
- **B 段**：设计提示词的校验失败和人工评审退回，按设计顺序的分布（后面的对象是否明显更差）；开始退化时大约是第几个对象。

根据结果决定：

| 实测结果 | 实施范围 |
|---|---|
| A 段、B 段都退化 | 全部实施 |
| 只有 B 段退化 | 只实施 `apply-designs` 与设计者派发 |
| 只有 A 段退化 | 只实施接力派发 |
| 都没有明显退化 | 只保留 5.1，dispatch 不实施 |

同时依据实测结果校准第六节的分批字数和 B 段门槛。这份记录写进实施验收文档，是一次性的人工记录，不是工具功能，不新增日志或统计。

## 十一、风险

| 风险 | 应对 |
|---|---|
| 接力者只看到已有条目、看不到前文原文，误把前文对象当新对象 | 已有条目带 sourceRefs，接力者按需定向回读；拿不准时新登记并写明疑点，由按对象分组的核验处理 |
| 后面的接力者擅自改坏前面的判定 | 每位接力者写新文件，不覆盖旧 draft；核验按对象回读全部出处；可以从上一份 draft 重新派发 |
| 草稿条目累积，后段接力者的输入变大 | 条目体量远小于原文；实测中如果成为瓶颈，再考虑只传条目摘要 |
| A 段墙钟时间比并行长 | 不是本方案的目标；实测后如确有需要，再另行评估并行 |
| 设计者给同名角色写出相似外观 | 同名或容易混淆的身份分在同一组 |
| 工具白名单不是沙箱，subagent 可能写出界 | 每个 subagent 只有自己的输出路径；apply-designs 只在完整校验通过后写回 |

## 十二、实施记录

与方案文字的差异，均在实施中按现有代码确定：

- **art 设计字段包含 `changes`。** 现有 `identityBasis` 把 changes 视为设计字段（不进入身份摘要），所以 apply-designs 接受它；variantOf 仍由接力者登记。
- **art 设计文件必须带 `designStatus`**（planned 或 ready），否则写回后状态与内容不一致。
- **art 的 complete 范围需要 `totalEpisodes`。** 现有来源检查要求声明，dispatch 写明由最后一位接力者填写。
- **基准缺少设计时，变体设计也能通过现有 validate。** 方案已经删去变体依赖检查，依靠「基准与变体同组」保证顺序；apply-designs 按 ID 列问题时，会连同同组的基准一起检查变体。
- characters 的校验流程抽成 `castChecks`，validate 与 apply-designs 共用同一套检查。
- 审查后修正：apply-designs 按 ID 列问题时，扣除原文件本身就有的问题，单独列为「原文件本身的问题」，避免把每份设计都退回；art 的 `changes` 只接受写在变体资产上；补测试覆盖 art 的 outline 文档 ID 对账。
- 仓库级 `scripts/strategy-pipeline-selftest.mjs` 在基线 `60261b5` 上就失败（样例 cast 的画风段格式），与本次改动无关，未在本次处理。
