## 一、结论与目标

保留 `image.sheet` 作为完整设定图正文。以“代码结构检查 → 大模型内容审核 → 图片生成 → 视觉审核 → 正式交接”组成完整质量流程，覆盖场景、物品、角色及现有变体。

不拼接 `image.prompt`，不切换生成字段，不新增提示词编译器，不重构资产身份、下游映射或制作工作单。

本次需要达到五个目标：

1. 只有版式、灯光、画风和纯净固定段，没有具体主体描述的请求，在导出图片计划前被代码阻断。
2. 生成前由大模型对照资产定义审核实际请求，发现主体写错、锚点遗漏、状态冲突等语义问题。不能只判断 Subject 段存在。
3. 生成后由具备视觉能力的模型查看实际图片，判断主体、结构、外观、版式和状态是否符合要求。基准图通过后才能生成依赖它的变体。
4. 成图通过视觉审核后才能作为已审核资产正式交接下游。生成成功、文件存在或报告挂图均不能代替审核。
5. 报告、图片计划和请求之间的字段用途明确，不在任务导出时隐式改写正文。

检查职责必须分开：

| 层级 | 执行方 | 能确认什么 | 不能代替什么 |
| --- | --- | --- | --- |
| 结构检查 | 本地代码 | 段落、固定句、参数、引用和文件等确定性约束 | 不能理解主体语义，也不能判断图片正确 |
| 提示词内容审核 | 执行 agent 发起单独的大模型审核；明确记录的人工审核可替代 | 实际请求是否符合原剧本、资产定义和制作要求 | 不能证明模型最终画对 |
| 图片视觉审核 | 执行 agent 调用具备视觉能力的模型读取成图；明确记录的人工看图可替代 | 实际图片是否满足主体、锚点、布局、状态和可用性要求 | 不能以文本描述、生成回执或文件元数据替代看图 |

本地 CLI 保持离线，不自动调用大模型，不通过正则表达式模拟语义或视觉审核。执行 agent 负责组织并执行后两项审核及交接门禁。`validate` 或 `images` 成功只代表本地检查或离线计划通过，不代表已经获得生成或下游投产放行。

但是，代码并不要求 sheet 存在独立主体段。对 skill 自有样例进行纯内存删段实验后，只有通用模板的场景、物品和角色正文仍可通过检查。

### 2.3 关联问题

| 问题 | 当前实现 | 影响 |
| --- | --- | --- |
| 主体完整性缺失 | sheet 主要检查非空、版式、画风、画幅和固定句 | 模板齐全即可通过，不能发现漏写主体 |
| 角色差异检查对象错位 | 相似度比较 `image.prompt`，不比较实际发送的 sheet 主体 | 插画不同不能证明设定图不同 |
| 变体检查不完整 | 道具后续状态主要检查非空和纯净段，没有逐任务完整检查画幅与画风 | 基准正确不代表变体请求正确 |

| 报告用途不突出 | 角色报告整块展示 image JSON | 容易把独立插画提示词误认为实际设定图请求 |

## 三、现行字段分工与调用链

### 3.1 两条提示词是不同产物

| 字段 | 用途 | 是否进入现有设定图计划 |
| --- | --- | --- |
| `image.prompt` | 角色表现性插画、场景单张空景、物品单张白底展示图 | 不进入 |
| `image.promptLocal` | 角色独立插画提示词的本地语言译文 | 不进入 |
| `image.sheet` | 完整的基准设定图；场景变体也写入自己的 sheet | 进入 |
| `image.negativePrompt` | 反向提示词 | 随对应任务传递 |
| `lighting[0].prompt` | 场景基准光影锁说明 | 不自动拼入，作者须落实到 sheet |
| `states[0].prompt` | 物品基准状态说明 | 不自动拼入，作者须落实到 sheet |
| `states[1...].prompt` | 物品后续状态的完整变体提示词 | 每个状态单独进入 |

独立插画可能使用方向光、浅景深、单一机位和剧情姿态。物品单张展示图不画人物，三格设定图右格却要画匿名尺寸参照。因此不能把 `image.prompt` 当成无构图的主体块直接拼接。

### 3.2 实际调用链

```text
原剧本与阶段资产
  → CLI 身份、来源及可选上游核验
  → 设计与制作参数检查
  → imageJobsFrom
      → 基准图读取 image.sheet
      → 物品后续状态读取 states[n].prompt
  → mediaPlan
      → 选择任务、补齐依赖、输出正文与参数
  → 执行 agent 按目标模型 schema 构造请求
  → 外部生成工具
```

主要代码位置：

- `skills/mint-art/scripts/mint-art.mjs`：`visualGateReport`、`validateVisualArt`、`validateArt`、`imageJobsFrom` 及 images CLI。
- `skills/mint-characters/scripts/mint-characters.mjs`：`sheetLayoutProblems`、`validateCast`、`productionProblems`、`imageJobsFrom`。
- 两个 skill 各自的 `scripts/lib/media-plan.mjs`：原文交接，不承担主体补写。

### 3.3 修改后的审核与交接流程

```text
原剧本、资产定义与制作参数
  → 代码结构检查、来源核验及离线图片计划
  → 执行 agent 构造实际请求
  → 大模型内容审核实际请求
      → 未通过或待确认：返修正文，不提交生成
  → 核对必要授权，提交基准图生成
  → 下载、文件格式核验、实际图片视觉审核
      → 未通过或待确认：不放行为正式资产，不向依赖任务提供参考图
  → 基准图通过，才执行依赖它的变体任务
      → 每个变体也须先审核实际请求，再生成并视觉审核
  → 当前交接范围逐任务核验审核结果及输入是否仍然匹配
  → 更新报告，正式交接已审核资产
```

这里有两种不同交接：

- 向生成工具交接请求之前，执行代码检查和提示词内容审核；尚未生成图片时不要求图片视觉审核。
- 向下游制作交接图片资产之前，必须完成实际图片的视觉审核。不能把前一种交接成功当成后一种交接通过。

## 四、修改设计

### 4.1 为基准图规定唯一、明确的主体段

仍然把 `image.sheet` 保存为完整英文字符串，不增加第二份结构化主体数据，也不同时保存编译输入和编译结果。

在现有散文段落中增加明确边界：基准图必须包含一个以 `Subject:` 开头的独立段落。

文本规则：

1. 标记位于段落开头，不能藏在版式或画风段内部。
2. 每条基准图提示词只允许一个 `Subject:` 段。
3. 标记后必须有非空正文；第一个空行结束该段。
4. 段内允许普通换行，检查时规整空白。
5. 版式、尺寸参照、正面光、画风及纯净固定句不能代替主体正文，也不能通过在 Subject 后照抄固定段冒充主体描述。
6. 不使用单词数量、英文类别关键词或正文长度，声称主体在语义上完整。

各类型的内容责任：

| 类型 | Subject 段的内容责任 |
| --- | --- |
| 物品基准 | 类别、形状、材质、颜色、可见锚点及基准状态；实际尺寸仍按现有版式要求填写 |
| 场景基准 | 地点类型、空间结构、关键物件及方位；四方向与平面图必须对应 |
| 人物基准 | 年龄段、地域文化、外貌、体型、发型和永久特征；服装与细节仍按指南完整填写 |
| 非人主体与群像 | 按现有类型写主体构成、辨识特征、数量或形态，不强套人类五官和服装要求 |

通用模型仍按版式、主体、细节、画风、纯净段组织。Midjourney 保留主体前置规则，将 Subject 段放在版式之前，段内首先描述媒介与主体。模型适配是同一现行契约的模型规则，不是旧格式兼容分支。

以下仅说明结构，不是可直接提交的完整提示词：

```text
<版式段>

Subject: A single black SUV with matte dark paint, square headlight clusters and red-brown mud along the lower body and wheel arches...

<正面光或场景光照>

Overall style: <production 的渲染句及适用质感>

<完整纯净画质段>
```

### 4.2 基准与变体分别检查

不能要求所有变体重新写完整身份锁。现有变体规则要求只点名保持项，避免重新描述未变化的结构。

| 任务类型 | 正文结构要求 |
| --- | --- |
| 场景、物品、角色基准 | 独立且非空的 Subject 段，以及对应类型的完整设定图结构 |
| 通用模型场景变体 | 参考指向、非空保持项、非空改动；检查自己的画幅、画风和纯净段 |
| 通用模型物品状态变体 | 参考基准图，保持三格及尺寸参照，写明非空状态改动；检查完整技术段 |
| Midjourney 变体 | 使用现有主体锚点、参考和最终状态写法，不强套通用 keep/change 指令 |

参考依赖仍来自现有 `variantOf` 或物品基准任务。正文里的 reference 字样不能代替任务依赖。

不新增人物变体槽位，不修改物品状态 ID，不扩展下游变体选择能力。相关架构议题继续与[资产变体问题文档](资产变体-问题分析与TODO.md)分开处理；本次只覆盖已经存在的任务正文检查。

### 4.3 统一检查所有实际任务

两个 skill 各自包含一个小型本地正文检查模块，例如 `scripts/lib/sheet-prompt.mjs`。不得跨 skill 导入，也不依赖外部 skill 完成校验。

检查模块接收正文、资产类型、模型、是否变体、生产参数等明确上下文，返回结构违规与需要内容复核的提示。

统一覆盖：

- 主体段或变体内容段。
- 对应类型的版式。
- 生产参数中的实际画幅。
- 对应画风的渲染句。
- 角色、物品所需正面光或场景光照结构。
- 纯净固定段原文，以及它确实位于正文末尾。
- 英文机器字段和已有名称约束。

调用规则：

1. validate、checkup、images 调用同一套正文检查，避免正式校验与出图入口结果不同。
2. `imageJobsFrom` 自身检查实际输出正文，不依赖调用方事先执行 validate。
3. CLI 提供已有 cast 名称等上下文；不能在 images 路径丢弃已提供的名称检查信息。
4. 内存 API 不读取来源文件，也不能声称已核验原件。来源字节、引用范围和生命周期检查继续由现有 CLI 边界负责。
5. 缺少 production 时，独立设计仍可检查文本结构；无法检查的画风和画幅明确 skipped。图片计划继续要求完整 production，不提供默认模型。
6. `designStatus: none` 的身份登记不要求设定图；planned 设计不进入生成计划；ready 才生成任务。

### 4.4 生成前执行大模型内容审核

这项审核检查语义，不由本地代码判断。执行 agent 必须在编写后发起一次单独的审核调用，提供当前资产依据和最终请求，不能把编写时的自评或结构校验通过直接作为审核结论。可以使用同一模型的独立审核调用，不要求新增第三方审核 skill。

审核输入至少包含：

- 原剧本中与本资产有关的原文片段、事实引用及明确的制作补定。
- 资产 ID、名称、summary、anchors，以及角色画像等适用定义。
- 场景 `lighting[0]`、物品 `states[0]`，或变体的基准定义、保持项和改动。
- production 中适用的画风、画幅和模型要求。
- 真正交给生成工具的请求：完整正向正文、反向约束、参数和参考素材顺序。不能只审核 `image.prompt` 或只读 Subject 段。

审核模型逐项判断：

| 检查对象 | 内容审核要求 |
| --- | --- |
| 所有资产 | 主体类别正确；颜色、材质、形状、比例及辨识锚点没有遗漏、偷换或无依据新增；正反向约束不冲突 |
| 场景 | 四方向及平面图的空间关系一致；关键物件的方位与数量正确；光源、方向和基准光照没有互相矛盾 |
| 物品 | 描述的是本件物品；白底和匿名尺寸参照不与主体要求冲突；基准状态正确 |
| 角色、非人及群像 | 外貌、体型、服装、永久特征或群体构成符合定义；角色之间有依据可辨识；不误带剧情道具或其他角色的身份 |
| 变体 | 使用正确基准；保持项明确；只改变指定内容；没有把新的身份、布局或材质改动藏进状态描述 |
| 最终请求 | 适配模型时未丢弃、改写或新增未经审核的约束，参考素材对应正确任务 |

例如，`Subject: A yellow bicycle...` 可以通过结构检查，但在资产定义为黑色越野车时，内容审核必须判为需返修，并指出主体类别和颜色错误。

不要求基准说明在 sheet 中逐字出现。自然语言可以使用不同措辞；原件里的现场摆放也可能不适用于单件白底设定图。例如 Demo P01 的状态说明包含两辆车和夜间湿坡，不能机械复制到单件物品基准图。`image.prompt` 只能辅助对照，不能取代原剧本和资产定义成为唯一依据。

审核输出使用“通过／需返修／待确认”，并列出对应资产、具体问题和依据。需返修或待确认均不能提交生成。返修后重新执行相关结构检查与内容审核；请求正文、反向约束、参数或参考素材发生实质变化后，不能沿用旧结论。

执行 agent 在阶段交接报告中记录当前审核结果、依据及对应输入，规则见 4.9。不新增 cast/art 审核字段，不把身份确认当成设计确认，不由脚本自动批准语义。无法调用审核模型且没有实际人工复核时，记录待确认并停止生成，不自动降级为结构检查。

### 4.5 修正角色区分度检查的对象与表述

当前 75% 相似度阈值针对独立插画提示词建立，不能直接转用于设定图。

修改要求：

- 原有 `image.prompt` 相似度检查明确命名为独立插画提示词相似度。
- 增加实际设定图主体内容的重复检查，使用 Subject 内容，而不是整条 sheet。
- 排除版式、画风、正面光和纯净固定段，避免模板导致误报。
- 不以原 75% 阈值硬判设定图是否合格。
- 不同角色主体内容完全重复时，明确输出需要内容复核的提示；该提示不是语义通过，也不引入新的批准字段。
- 内容是否足够区分，仍由模型或人工对照画像判断。

现有明确允许两个人物 sheet 完全相同且不报告的测试，需要改成能够发现重复主体的测试。

### 4.6 取消风格参考路径的隐式正文追加

角色 `imageJobsFrom` 的 styleRef 分支当前执行：

```javascript
j.prompt = `${j.prompt} ${STYLE_REF_LINE}`;
```

本次改为：

- 保留风格参考图片及任务依赖。
- 需要风格匹配说明时，由作者写入源 sheet 的纯净段之前。
- 明确风格参考只借画风，不借另一个角色的身份；同步修正文档里基准图参考说明的边界。
- 导出函数不再追加该指令，也不插入独立插画正文。
- 检查最终任务正文，而不只是改写前的源字段。

基准任务应满足 `job.prompt === image.sheet`；物品后续状态任务应满足 `job.prompt === states[n].prompt`。反向词按现有交接方式单独携带，外部请求适配不能静默丢弃约束。

### 4.7 报告区分实际生成正文与独立插画

美术和角色报告优先展示：

1. 实际设定图生成正文。
2. 对应反向提示词。
3. 独立插画／展示图提示词，并明确说明未进入本次图片计划。

角色报告不再只把整个 image JSON 当作唯一提示词展示。原始 JSON 导出仍完整保留，不把展示默认值写回数据。

报告同时区分结构检查、提示词内容审核和图片视觉审核。文件存在不代表图片与当前设计一致，不得把挂图成功写成审核通过。报告展示当前逐任务结果及交接范围，不能把未审核或审核失败的图片与通过图片一起标成正式可用。

### 4.8 生成后执行实际图片的视觉审核

下载并完成非空文件、真实格式等代码核验后，执行 agent 必须将实际图片交给具备视觉能力的模型审核。需要时读取原图及局部裁剪，不能只根据文件名、请求文字、生成成功回执或另一段图片描述推断图像合格。

审核输入包含实际图片、当前资产依据、已通过内容审核的实际请求，以及适用的基准参考图。变体必须同时查看实际使用的基准图和变体成图；人物区分度、黑红伞等成组差异需要时并排比较。

| 检查面 | 视觉审核要求 |
| --- | --- |
| 主体忠实度 | 类别、颜色、材质、可见标记和基准状态符合资产定义与提示词；例如黑色越野车不能变成银色皮卡 |
| 结构与比例 | 没有明显几何融化、缺件、多件、部件连接错误或尺寸参照失真 |
| 多视图一致性 | 各格为同一对象，结构、颜色、材质、服装和比例一致；不把不同车型或不同角色放在同一张设定图里 |
| 场景布局 | 四方向与平面图对应，空间关系、关键物件数量和方位正确，光照符合定义，无多余人物 |
| 角色身份 | 脸部、体型、发型、永久特征和服装正确，版式与主体类型相符，不混入风格参考人物的身份 |
| 物品版式 | 正面、中间角度及尺寸参照清楚，白底和完整入画符合要求；匿名参照不被当作剧情人物 |
| 变体一致性 | 基准身份与指定保持项不变，指定状态改动确实出现，没有额外改变结构或布局 |
| 可用性与禁用元素 | 关键锚点可辨识，没有妨碍参考使用的模糊、裁切、噪点、明显畸形、多余文字、水印或商标 |

视觉审核同样输出“通过／需返修／待确认”，逐项说明问题位置和依据。看不清的锚点或无法确认的状态记录待确认，不能以整体观感不错代替逐项核对，也不能声称看图能证明精确物理尺寸。

基准图必须先通过视觉审核，再挂载为依赖任务的参考。每个变体也要独立通过视觉审核。若变体以另一变体为直接参考，则其直接参考图也必须已通过审核。

执行 agent 须同步记录图片审核结论和文件依据。正文正确但图片错误时，优先判为生成结果问题；正文错误时返回内容修订。任何重生成都属于可能计费的新任务，必须核对现有授权是否明确覆盖，不因审核失败自动无限重投。重生成或编辑产生的新文件必须重新视觉审核，不能继承被替换图片的结论。

没有视觉能力时，可交付“已生成、待审核”的材料并明确阻塞，但不得正式放行为可投产图片，也不得提供给依赖它的变体任务。实际人工看图并记录明确结论，可以替代视觉模型审核。

### 4.9 交接门禁、审核记录与失效规则

执行 agent 负责以下放行条件：

| 动作 | 必须满足的条件 |
| --- | --- |
| 导出离线图片计划 | 代码结构、来源及制作参数等现有必需检查通过；计划本身不是付费提交授权 |
| 向生成工具正式提交请求 | 最终请求内容审核通过，所需参考图已经视觉审核通过，必要生成授权有效 |
| 生成依赖基准的变体 | 基准图及实际使用的直接参考图已通过视觉审核，变体请求内容审核通过 |
| 向下游正式交接图片资产 | 本次交接范围内的请求内容审核和实际图片视觉审核均通过，且结论与当前输入及文件仍然匹配 |
| 仅身份登记、仅文本或用户明确不出图 | 按用户限定交付，不新增图片要求；未生成或未审核状态不能冒充图片已可用 |

审核记录写入由执行 agent 维护的独立阶段交接说明：角色为 `characters/cast-handoff.md`，美术为 `art/art-handoff.md`。它们记录当前交接范围与当前审核结论，不保存失败累计、重试统计或历史台账，不新增 cast/art schema。

自动 render 仍负责原有报告，不覆盖上述交接说明；报告明确给出交接说明入口，并提示以匹配当前输入和图片的审核记录为准。没有记录时展示待审核，不能根据文件存在或复制旧结论宣告通过。

每个任务记录当前结论及必要证据：

- 资产与任务 ID、请求文件位置及当前请求摘要，适用的资产输入摘要或设计指纹。
- 内容审核执行方、结论、问题及依据。
- 实际图片路径和文件摘要，变体实际使用的参考图路径及摘要。
- 视觉审核执行方、结论、问题位置及依据。
- 本次正式交接的范围与尚未放行的任务。

摘要复用现有标准库计算方式，只绑定审核对象，不改变现有资产映射或工作单哈希算法。已存在文件、相同 ID 或相同路径都不能证明旧审核仍然有效。

变更后只重核实际受影响的范围：

1. 资产依据、请求正文、反向约束、参数或参考素材改变，相关内容审核结论须重新核验。即使图片字节未变，也不能自动视为符合新的要求。
2. 图片被替换、编辑或重新生成，旧视觉结论不能沿用。
3. 基准参考图改变，依赖它的变体不得自动沿用旧审核。须核对变体实际使用的参考图以及新旧差异；必要时重新生成和审核，不自动作废无关任务。
4. 审核结论缺失、待确认、需返修或与当前输入不匹配，都不能正式放行图片资产。

本方案中的内容审核、视觉审核与交接门禁由执行 agent 执行并记录，不宣称现有 `validate`／`images` 能验证大模型是否实际看过文本或图片，也不新增离线 CLI 自动调用模型的能力。结构检查通过但缺少后两项审核时，必须保持待审核，不能据此宣布阶段图片交付完成。身份登记或待审核材料可以单独交付，但必须与正式可投产图片交接区分。
