# 长剧本分块解析、子代理协作与跨集连续性：调研参考

## 0. 结论

**可以使用 subagent，但不能把方案简化为“一集一个 agent，最后拼接”。**

建议采用：

> 场次感知分块 → 独立提取有出处的局部事实 → 统一归并身份与跨集依赖 → 按需组装上下文 → 结构化正文 → 独立核验原文及跨集连续性。

核心不是让每个 agent 记住全剧，而是让它们从同一份已核验资料中，读取当前任务需要的事实和原文。

直接回答：

| 问题 | 建议 |
| --- | --- |
| 文本太长，能否分批读取？ | 必须支持。按集、场、完整话轮分块，并限制实际上下文负载，而非只限制集数。 |
| 能否使用 subagent？ | 可以。每个任务使用新上下文，详细结果落文件，主会话只接收路径、范围与待处理问题。 |
| 分集有关联，能否全部并行？ | 局部事实提取可以并行；身份归并、状态传播和跨集判断必须经过统一协调。 |
| 如何减少剧情割裂？ | 显式记录身份、事件、故事时间、揭晓顺序、人物知情状态和道具交接；通过来源引用传递，不只传上一集摘要。 |
| 是否需要审核 agent？ | 建议需要独立审核角色，但不能让一个审核会话一次读完整部剧。审核任务也要分块，并增加跨边界、跨远距离依赖检查。 |
| 多 agent 是否保证正确？ | 不保证。结构检查、来源核验、独立内容审核和小规模人工基准必须配合。 |
| 是否需要向量数据库或完整 GraphRAG？ | 首版不需要。文件、稳定引用、实体与事件索引足以实现最小方案。 |

**推荐最小角色：读取者、归并者、审核者。主会话负责调度。**角色不等于常驻进程，更不等于每个角色持有全剧上下文。

## 2. 现有代码到底支持什么？

下面区分实际代码能力与指南约定。行号以本次基线为准。

### 2.1 outline 有切块工具，但仍是小说切卷逻辑

位置：`skills/mint-outline/scripts/mint-outline.mjs:76–131,175–182`。

| 当前实现 | 对长剧本的影响 |
| --- | --- |
| `CHAPTER_RE` 识别章、回、节、卷、部、Chapter，不识别“第 N 集”或场次 | 剧本通常落入固定长度切分，不能依赖它保留集场边界。 |
| 章节模式默认每卷 15 个起点 | 章节长短不一，单卷没有字符数上限。 |
| 长度模式每块 20,000、重叠 500 | 单位是 JavaScript 字符串长度，即 UTF-16 单位，不是 token。 |
| 长度模式直接 `slice` | 可能切断台词、括注和事件。 |
| 最多 60 块 | 超长输入会返回 `truncated:true`，CLI 不因此返回失败。 |
| 换行规范化并 `trim` | 结果不是原始字节的无损切片。 |
| 输出 `vol-00.txt` 等纯文本 | 没有保存来源区间、块清单、源文件哈希或正式覆盖关系。 |
| 重跑写入同名文件 | 没有本次有效块清单；旧的多余块文件不会自动消失。 |

**注意：本地程序把文本读入内存，与把全文送进模型上下文是两件事。**`readFileSync` 本身不会造成模型注意力漂移。需要控制的是工具返回给模型的材料量和后续累计上下文。

### 2.2 分批与连续性主要写在指南中

- `skills/mint-outline/references/volume-pass.md:1–21`：来源范围、覆盖说明、别名、逐字证据只是摘要格式约定，没有对应的合并器与核验器。
- `skills/mint-outline/references/创作指南.md:55–57`：建议每批不超过十集。
- `skills/mint-script/references/创作指南.md:47–53`：建议每批最多三集，并交接位置、知情范围、道具和承诺。
- `skills/mint-script/scripts/mint-script.mjs:344–355`：seed 只生成集号、目标、B ID 和空场次，没有生成前情与状态包。

这些批次数量不受当前代码强制限制。没有发现 outline/script 的分块任务调度、跨块身份归并、共享剧情状态或完整读取检查点实现。

### 2.3 已有引用检查值得保留，但不能当成语义核验

- `skills/mint-outline/scripts/lib/outline-core.mjs:157–211`：检查集号、资产引用、Q 的提出与回收；固定返回 `contentReview: 'not-performed'`。
- `skills/mint-script/scripts/mint-script.mjs:229–241,298–339`：`beatClaims` 检查 B ID、坐标、顺序和重叠，不判断正文是否真正表达了事件。

现有坐标是数组位置，不是稳定的原文位置。替换正文后，旧坐标仍可能合法，但语义已经变化。

### 2.4 creation 提供了协作范式，不是全剧审核器

关键位置：

- `skills/mint-creation/references/dispatch.md:5–166`。
- `skills/mint-creation/scripts/mint-creation.mjs:1896–1958,2051–2160`。

- `agents/pi/mint-video-prompt-writer.md`、`agents/pi/mint-video-prompt-reviewer.md`。

已有能力：

1. 编写与审核使用不同 subagent 上下文。
2. 先确定性检查，再做内容审核。
3. 工作单记录本轮意见与状态。
4. 批准绑定内容及部分输入；变化后在 status/apply/export/videos 中重新核对。
5. 文档要求同一工作单不能并发写入，设有止损约定。

实际边界：

- `dispatchBrief` 只包含当集正文与当集计划；资产表虽取全局列表，但主要是 ID、名称和图片信息，不是全剧情状态。

- 仓库没有自动启动子代理并完成循环的调度器；调度主要由主会话按指南执行。
- 单写者与三轮止损部分属于行为约定，不是文件锁或强制执行边界。
- 不能直接复用视频工作单格式或哈希函数，就宣称已经完成剧本解析审核。

**建议复用原则和交互习惯，不让 outline/script import 兄弟 skill 的代码。**

### 2.5 批次文件与自动发现存在现实约束

`skills/mint-script/scripts/lib/downstream.mjs:13–26` 自动读取阶段目录下唯一候选 JSON，多候选报错。

## 3. 公开研究给出的启示

### 3.1 长窗口不等于有效理解窗口

**Lost in the Middle** 在多文档问答和键值检索中发现，相关信息的位置会影响结果，位于中部时可能明显退化。[R1]

**RULER** 不只测单个信息检索，还测多跳追踪和聚合；实验说明“能找到一根针”不能证明长上下文综合理解能力。[R2]

对本项目的启示：

- 不把模型最大窗口直接当作工作块大小。
- 验证人物身份、多步交接和远距离因果，不能只测能否找出某句台词。
- 不声称所有当前模型都在同一长度退化；需要按实际使用模型校准。

### 3.2 分层摘要与滚动摘要各有代价

**BooookScore** 比较分层合并与滚动更新。其实验中，分层合并通常更连贯，但细节更少；滚动更新更详细，但出现更多连贯性问题。[R3]

对本项目的启示：

- 全剧概览可以分层生成。
- 人物身份、道具状态、伏笔依据不能只保存在反复压缩的摘要中。
- 不能把“摘要读起来顺”当成“原文事实没有丢失”。

### 3.3 叙事错误恰好集中在事件与人物状态

**FABLES** 基于 26 本书、3,158 条摘要断言进行人工核验。作者发现，不忠实断言大量涉及事件及角色/关系状态，而且经常需要间接、多步推理才能反驳。研究中的 LLM 自动评估器未能稳定识别这些错误。[R4]

对本项目的启示：

- 审核不能只检查 JSON 或摘要内部是否自洽。
- 审核者必须能够读原文，并沿人物、道具和事件链回查。
- 审核 agent 有价值，但不能作为绝对正确的裁判。

### 3.4 顺序交接有用，但不能只传一段不断改写的摘要

**Chain of Agents** 让各 worker 顺序读取不同片段，传递中间信息，再由 manager 汇总；它不是纯并行的独立摘要拼接。[R5]

对本项目的启示：

- 跨集依赖需要显式交接。
- 需要状态传播的步骤不能为了并发而取消顺序。
- 本项目应保留结构化证据和回查入口，减少自然语言接力造成的信息损耗。

### 3.5 场次是合适的工作边界，但不能牺牲原台词

**NexusSum** 针对书籍、电影与电视剧本，采用场次相关分块和分阶段摘要，还将对白转为第三人称描述。[R6]

可借鉴：按场次组织语义完整的工作单元、分离局部处理与全局归纳。

不可照搬：把对白改写为描述后，拿它替代正式 script 正文。该研究的任务是摘要，不是逐字保留剧本。

### 3.6 结构化实体记忆直接针对跨块状态问题

**Entity Blackboard** 的官方论文摘要明确指出：独立分块摘要没有追踪实体状态变化，会造成连贯性和一致性问题。其方法在顺序处理中更新结构化实体记忆，并限制噪声写入。[R7]

对本项目的启示：

- “人物现在处于什么状态”应有显式记录。
- 共享记忆不能允许所有 worker 无审核覆盖。
- 状态必须绑定来源与时间，不能把最新值用于所有历史场次。

本次核实了该文官方摘要与出版信息，未复现其系统，也不依据摘要推断内部字段或性能细节。

### 3.7 多代理解决上下文隔离，不自动解决协调

Anthropic 的上下文工程文章建议结合按需读取、结构化笔记和干净的子代理上下文。[R8]

其多代理研究系统经验强调明确任务边界、文件化产物交接，同时指出共享依赖密集的任务不适合直接并行，成本可能显著上升。[R9]

对本项目的启示：

- 并行事实提取，而不是并行决定全剧事实。
- 子代理返回文件引用，不把全部结果重新塞回主会话。
- 主会话不承担每一集的细读与语义修补。

### 3.8 检索和图索引是补充，不是完整阅读的替代品

Contextual Retrieval 说明孤立切块会丢掉必要上下文。[R10]

GraphRAG 说明局部 top-k 检索与全局主题总结是不同问题。[R11]

对本项目的启示：

- 给原文块附上作品、集场、时间线和身份上下文。
- 先确保全源覆盖，再用检索处理远距离依赖。
- 首版可用 ID、别名、源位置和事件关系索引；不必先引入向量数据库或图数据库。

### 3.9 把长文本当成外部数据，而不是聊天历史

**Recursive Language Models** 将长输入放在可编程外部环境中，模型检查片段并调用子任务。其研究也报告了成本与运行时间的长尾。[R12]

适合借鉴文件化原文、有限范围读取和分解任务。不建议首版实现无限递归 agent 系统。

### 3.10 自审不是独立核验

关于 intrinsic self-correction 的研究指出，缺少外部反馈时，模型未必能纠正自身推理错误。[R13]

这不能推导出“同一个模型绝不能审核”。本项目真正需要的是：独立上下文、原文依据、明确核验任务和允许保持未知，而不是让作者重复说一次“我检查过了”。

## 4. 方案比较

| 方案 | 优点 | 主要问题 | 本项目建议 |
| --- | --- | --- | --- |
| 单 agent 读取全剧 | 简单、无需协调 | 容量与注意力问题，难复核覆盖 | 只适合较短输入和对照实验 |
| 单 agent 顺序读、自动压缩 | 能处理更多材料 | 同一会话不断累积，摘要会遗忘细节 | 仅作降级，不作为唯一状态机制 |
| 每集独立 agent，直接合并 | 并行度高 | 别名、伏笔、交接和时间关系容易割裂 | 不采用为最终流程 |
| agent 顺序接力摘要 | 能传前情 | 速度受串行限制，早期错误可能传播 | 借鉴交接，不只传摘要 |
| RAG 按问题找片段 | 节省上下文 | 无法证明全部原文已覆盖 | 用于定向补读 |
| 完整 GraphRAG/多角色辩论 | 能处理复杂关系 | 建设与调用成本高，仍依赖正确抽取 | 首版不引入 |
| 有出处的局部提取＋统一归并＋依赖包＋独立审核 | 保留并行，能处理跨集事实 | 需要最小任务与证据协议 | 推荐 |

## 5. 推荐架构：并行提取，统一事实，按依赖审核

```text
原始剧本：保存原件与来源版本
        ↓
确定性索引：集场、源区间、覆盖清单、分块清单
        ↓
读取者 subagent × N：各自读取核心范围＋必要边界原文
        ↓
局部记录：出现、事件、状态变化、原文引用、未知项
        ↓
结构与来源检查
        ↓
归并者：按候选身份、事件链和时间线分批处理
        ↓
统一的已接受事实与 ID 映射
        ↓
跨集连续性审核＋有问题的原文定向补读
        ↓
冻结本轮解析快照
        ├── 生成 outline：主线、分集、事件与资产身份
        └── script worker：当前原文＋相关事实包 → 正文分片
                    ↓
          原文忠实性审核＋必要跨集复核
                    ↓
          确定性组装正式产物、现有检查、制作交接
```

### 5.1 第一遍不要求 worker 理解全剧

每个读取者只对自己实际读到的范围负责：

- 提取明确发生的动作、对白与出现。
- 区分叙述事实、角色陈述、猜测、梦境和回忆。
- 对身份、代词和省略关系提出候选，不擅自定稿。
- 记录原文位置和必要引文。
- 记录“此处需要前情才能解释”的依赖请求。

**后面一集看不懂前面发生了什么，不等于这个 worker 失败。**诚实保留未知，比用常识补完剧情更安全。

局部记录允许临时身份，例如 `E012-C03:M02`。worker 不自行分配正式 C/S/P/B ID，避免多个 agent 分配出不同的 C01。

### 5.2 全局归并不等于把全部记录交给一个超长上下文

确定性程序先按原文位置、名称候选和明确引用建立索引。

归并者按有限范围处理：

- 一个身份候选组及其相关原文。
- 一条道具交接链。
- 一条有证据的因果或承诺链。
- 一个时间线内的连续状态变化。

代码负责聚合、排序、引用检查和提案应用；Agent 负责需要理解的身份与关系判断。不能把“语义归并”包装成纯确定性函数。

同名对象可能不同；不同名称可能同一对象。候选索引只是帮助查找，不是自动合并依据。原文链较长时分页处理并保留未决连接，不能把它再次压成不可回查的总摘要。

全剧概览从分集/阶段结果分层生成，始终保留到事件和原文的引用。概览用于导航，不承担唯一事实记忆。

### 5.3 统一发布，而非共享文件自由写入

- worker 只能写自己的任务目录。
- 归并者提交带来源的修改提案。
- 调度方通过本阶段工具检查并发布快照。
- 审核者只写结论和证据，不直接修改正文或身份表。
- 下一批只能读取已经发布的快照，不读取其他 worker 尚未完成的文件。

首版采用批次屏障和单一发布者即可。不需要数据库、分布式锁或持续运行的黑板服务。

工具白名单和提示词不是强安全沙箱；拥有 bash 的代理仍可能越权。因此要结合独立输出目录、禁止直接覆盖正式文件以及提交时校验。

## 6. 怎样切块，才能既短又不割裂？

### 6.1 层级优先，而非只按字符数

顺序：

1. 优先沿用原剧本分集边界。
2. 集内按原有场次组织。
3. 多个短场可以组成一个工作单元。
4. 超长场按完整动作段和完整话轮继续拆分。
5. 没有可识别边界时，先做边界候选识别，并保留原文覆盖与人工确认入口。

集是交付单位，场是常用读取单位，工作块是运行单位。三者不必相同。

### 6.2 核心范围与上下文范围分开

每块定义：

- `coreRange`：本任务拥有的正文范围，正式抽取覆盖以此计算。
- `contextRanges`：前后邻接的必要原文，只用于理解。

跨界事件可引用两侧证据，但事件只由约定的核心范围任务提交；另一任务登记引用或依赖，不重复生产同一正文。

所有核心范围应构成完整、不重叠的源区间分区。上下文重复不计为二次覆盖。禁止按台词字符串去重，因为同一句话在不同位置重复可能有叙事意义。

不能把固定 500 字重叠当成完整的连续性方案。它只能帮助切口附近，不会找回几十集之前的伏笔。

### 6.3 预算必须包含全部输入和输出

初始实验建议，不是行业标准或已验证配置：

- 常规任务从 1–3 场、约 4k–8k 原文 tokens 起试。
- 把简报、相关状态、必要引文和规则也计入输入，尝试将完整输入控制在约 12k–16k tokens 内。
- 为事实记录或正文输出另留预算；若输出接近限制，应拆任务，不截断结果。
- 初始并发 2–4 个，再依据模型、限流和实际成本调整。
- 密集对白、频繁身份转换、回忆与多人交接应缩小工作单元。

没有精确 tokenizer 时，使用明确标注的字符/字节预算与实际调用反馈校准，不能把中文字符数直接宣称为 token 数。不得为了预算自动丢掉相关依赖；超限就拆任务或先定向补读。

### 6.4 来源定位应可验证

建议首版保存原始文件哈希与确定的编码，正文引用使用原文件 UTF-8 字节区间，并附可读集场/行号。区间采用半开形式 `[start,end)`，确保落在合法字符边界。

若需要换行规范化，必须同时保留原件和映射，或选择不改变用于定位的原文。不能对 `trim` 后的文本坐标声称它属于原始文件。

定位规则、哈希和版本属于机器可验证部分。引文存在不等于语义推断成立，后者仍需内容审核。

## 7. 跨集连续性需要哪些信息？

### 7.1 不是一份无限增长的“前情摘要”

建议最小事实类型：

| 类型 | 需要表达的内容 |
| --- | --- |
| 身份 | 对象、别名、身份认定依据、何时揭晓 |
| 事件 | 谁在何处做了什么，结果是什么，依据在哪里 |
| 时间 | 原文顺序、故事时间/时间线；不知道时明确未知 |
| 状态变化 | 对象、属性、前后值、触发位置与作用范围 |
| 知情范围 | 谁知道、相信或怀疑什么，依据与获知位置 |
| 物件流转 | 同一实物的取放、持有人、交接、毁损 |
| 跨集依赖 | 当前事件依赖哪个此前事实、承诺或揭晓 |
| 未决问题 | 原文缺失、身份不明、互相矛盾、需要补读的位置 |

关系与状态按实际需要记录，不为每个背景人物创建庞大人物数据库。

### 7.2 至少区分三种“时间/知识”

1. **叙述顺序**：观众在第几集第几场看到信息。
2. **故事时间**：事件在故事世界中何时发生，可能是闪回。
3. **角色知情范围**：角色是否在场、听到、被告知，或仅在猜测。

全剧解析者知道最终身份，不意味着人物或观众在前面已经知道。

稳定 ID 可以统一对象，但展示名称和制作说明要遵守该处揭晓范围。不要直接给早期任务发送带最终身份的完整人物卡；可分离“内部身份映射”和“截至该处可展示的信息”。

这需要贯穿数据与消费端，而非仅修改提示词。当前 `skills/mint-script/scripts/mint-script.mjs:367–371,386–395` 按 speaker ID 查询全局人物名称，没有场次称呼参数。归并身份后若直接沿用现有渲染器，早期场次仍可能显示最终姓名。实施时需设计当前称呼的表达与渲染，不通过修改全局姓名或把同一人物拆成多个正式 ID 来规避。

### 7.3 状态不能只保存最后一个值

错误方式：

```text
钥匙持有人 = 许岚
```

必要表达：

```text
第 2 集：顾宁将钥匙交给许岚，有原文交接依据。
第 5 集：回忆发生在第 2 集之前，钥匙仍在顾宁手中。
第 8 集：当前时间线沿用第 2 集交接结果，除非有后续变更依据。
```

“原文没有再提”不等于状态归零，也不自动证明无限延续。对位置、服装、伤势、持有关系等不同属性，应区分明确延续、合理但未确认的推断和未知；不能把所有属性统一机械继承。

### 7.4 一个跨集示例

以下为本研究自有微型情境，只用于说明协议，不是任何 skill 的正式样例。

- 第 2 集：顾宁把刻有缺口的铜钥匙交给许岚。
- 第 5 集：闪回两年前，顾宁带着同一把钥匙进入旧站。
- 第 12 集：“灰衣人”递出钥匙；原文尚未说明其身份。
- 第 18 集：原文明示灰衣人是许岚。

正确处理：

1. 第 12 集读取者记录临时身份及交接，不凭钥匙就断定身份。
2. 第 18 集的证据可支持全剧身份归并，但保留揭晓发生于第 18 集。
3. 第 5 集使用过去时间线，不覆盖当前时间线的持有人。
4. 第 12 集的制作说明使用“灰衣人”，不提前揭示许岚。
5. 若第 12 集是另一把同款钥匙，必须根据原文区分，不能只按名称合并。
6. 审核按身份和道具链读取第 2、5、12、18 集相关原文，不需要四集全文同时进入上下文。

### 7.5 当前任务上下文包

由工具从已发布资料组装，避免主会话手工复述：

```text
任务身份与来源版本
当前核心原文＋必要边界原文
本任务涉及的 C/S/P ID 及当地称呼
截至当前剧情位置可使用的事实与状态
与当前事件直接关联的远距离原文依据
本任务相关 B ID、未决依赖、明确禁止补写的范围
输出契约和需要执行的检查
```

所有检索条目保留来源引用。依赖范围超出预算时拆成核验任务，不偷偷减少 top-k 后宣称上下文完整。

## 8. 需要怎样的审核 agent？

### 8.1 推荐一个独立角色，多个有限范围任务

不需要首版配置多名裁判投票。一个审核角色可以按任务启动多个独立实例。

| 审核层次 | 检查对象 | 目的 |
| --- | --- | --- |
| 来源忠实性 | 当前核心原文与抽取/正文 | 找遗漏、误引、错人、错误状态、无依据推断 |
| 切块与邻接边界 | 相邻块的边界及状态变化 | 找漏接、重复、代词断裂与交接遗漏 |
| 远距离依赖 | 身份、道具、承诺、因果、时间链 | 找非相邻集之间的矛盾和过早揭晓 |
| 全剧概览 | 分集索引、事件链、主线与结局依据 | 找主线遗漏和结构性误读，不替代逐块核验 |

最终审核不是把所有材料重读一遍，而是确认这些范围都有核验结果，并对冲突和高风险链定向回查。

### 8.2 审核者不能只读作者挑选的引文

仅验证已抽取断言，会漏掉“根本没有被抽取”的事件。

因此，每个核心范围都应有原文到记录的遗漏检查。审核者获得核心原文和回查工具，不只获得 worker 的摘要与自我评价。

需要同时做：

- **记录 → 原文**：断言有无依据，是否误解。
- **原文 → 记录**：关键对象、动作、状态和因果是否遗漏。

核心范围覆盖可以由代码检查；内容覆盖仍由审核者判断。二者不能混称“100% 理解覆盖”。

### 8.3 审核输入与输出

审核输入：冻结的源版本、任务范围、候选结果、相关事实快照和相关原文。

不输入：作者自评分、主会话预设结论、作者为自己产物作出的说服性解释。

审核输出至少包含：

- 结论与本次覆盖范围。
- 问题类型。
- 原文位置、结果位置和具体证据。
- 这是解析错误、来源本身矛盾，还是来源不足。
- 最小修正建议或需要补读的范围。

源码矛盾不能靠审核者擅自改剧情解决。可以准确交付“原文存在矛盾”。只有阻碍身份认定、正文归属或必要下游使用的问题，才阻断相关交付；正常未知和可保留歧义不应让全项目无限停滞。

### 8.4 状态、批准绑定与止损

可以沿用当前工作单的状态词习惯：`draft / in_review / changes_requested / blocked / approved`，但采用本阶段自己的最小数据结构。

批准应绑定：

- 被审核结果的内容哈希。
- 实际审阅的原文范围及其来源版本。
- 实际审阅的相关事实快照。
- 影响判断的任务要求和协议版本。

登记时必须核对审核者实际读取的输入快照，而非直接用登记时的最新资料冒充它已经看过。

首版采用保守失效策略：来源或已接受事实快照改变，相关派生判断重新核对；若无法判断影响范围，就让依赖该快照的语义批准失效。原文未变的纯局部抽取可按其输入键复用。

只按“已经消费过的事实 ID”做失效不够：新发现的别名或此前遗漏的事件可能改变检索结果。未来若做精确失效，还要绑定查询条件、索引版本和结果集合。首版不为省少量调用引入复杂依赖引擎。

止损建议沿用现有习惯：同一任务三轮仍有争议，交用户或主调度协调；不要无限自审。只保留当前状态与本轮问题，不新增失败累积日志或统计功能。

### 8.5 同一模型是否足够？

首版可以同一模型、不同上下文，先验证收益。

真正重要的是证据独立和任务独立。不同模型也可能共享错误；多模型投票不能替代原文。若人工基准显示相同类型的共同误判，再考虑对高风险链使用第二模型或人工复核。

## 9. 子代理调度与产物组织

### 9.1 优先采用简单、有限的调度

- 主会话创建清单，启动有限并发任务。
- 读取者处理一个工作单元后结束，不在同一上下文连续阅读几十集。
- worker 不继续启动子代理，防止任务树失控。
- 回报只包含产物路径、核心范围、输入版本、完成情况和未决项。
- 只有格式与来源检查通过的结果才能进入归并和审核。
- 缺块、超时、输出截断不等于部分成功，应在清单中明确标记。
- 恢复任务时按当前输入哈希核对，不按“文件已经存在”直接跳过。

本仓库可以借鉴 `references/dispatch.md` 中现成的 subagent/独立进程派发方式，不必新增通用调度框架。具体并发上限由运行时决定，不能把文档中的数值当成所有环境的保证。

### 9.2 文件布局建议

以下是概念布局，尚未发布为正式契约：

```text
项目/
├── production.json
├── outline/
│   ├── 作品-outline.json              正式结构、C/S/P/B ID 的所有者
│   ├── source/                       原件与源版本索引
│   ├── analysis/                     正式交接需要的来源、事实和依赖资料
│   └── .work/parse/<run>/
│       ├── manifest.json             本轮输入、任务范围、状态与输出引用
│       ├── tasks/<task>/             每个 worker 自己的结果及当前审核
│       └── proposals/                尚未发布的归并提案
└── script/
    ├── 作品-script.json               组装后的正式正文
    └── .work/import/<run>/            待组装的正文分片与核验结果
```

- 不把工作片段平铺为阶段根目录中的多个正式 JSON。
- 正式交接依赖的资料不能只存在于可删除的 `.work/`。
- `analysis/` 保存来源事实和关系，不维护另一份可独立修改的完整剧本。
- 正式 ID 由 outline 统一拥有；证据资料引用 ID，不自行建立第二套命名权威。
- 正式正文只由组装/修改流程更新 script JSON，Markdown 由它渲染。
- 发布 outline 与证据资料时使用同一版本清单；消费者拒绝不匹配的组合。
- 以上正式辅助资料需要显式设计读写契约，不是利用现有校验器忽略未知字段的捷径。

### 9.3 确定性组装应做什么？

1. 确认每个核心范围恰好有一份被接受的结果。
2. 核对输入版本、输出格式、来源区间和引用存在性。
3. 按原文顺序拼接，不按 worker 完成顺序拼接。
4. 应用已批准的临时身份到正式 ID 的映射。
5. 检查集号重复、缺失、顺序与来源范围。
6. 对可逐字验证的正文执行源文本比对。
7. 检查所有非正文源片段也有明确分类，不能为通过覆盖而一概标记忽略。
8. 生成一个正式 script，并继续执行现有阶段检查。

有序、完整的文本映射不能证明“动作还是台词”“谁在说话”的解释正确，这些仍需语义审核。

## 10. 与现有 skill 的融合边界

### outline

新增或改造来源索引、分块、覆盖检查、事实记录、身份归并提案和发布快照。删除小说入口假设，但保留有价值的稳定 ID 与结构检查。

当前 full 要求全剧集号连续、明确结尾和 required 问题回收。需要另行设计来源不完整时的诚实状态，不能为了全剧检查修改原文。

### script

增加原剧本范围输入、相关事实包、局部正文结果和确定性组装。沿用 beatClaims 的引用价值，但继续检查它是否适合表达实际源剧情。

script 不重复维护全局人物身份；发现错误时向 outline 提交带来源的修订请求。

### 人物与美术

读取已接受的事实和需要的状态变化，再做制作决定与视觉实现。不能把局部读取者的临时推断直接当出图设定。

### creation

后续可以把当前段有关的连续性事实加入 brief，但必须同时扩展批准绑定和核验范围。只增加字段而不改 `inputHashOf`，会造成“审核看过但变更不失效”。

不在本轮长剧本解析设计中顺带重写整套视频提示词流程。

### 自包含

数据交接可以跨阶段；实现代码和 references 不能依赖兄弟目录。小段协议检查需要各 skill 本地实现或持有副本，并通过独立复制测试，遵守仓库既有做法。

## 11. 实施优先级：先解决覆盖，再扩展智能

### 第一阶段：无损分块与任务清单

- 识别集场，超长场继续拆分。
- 保存原件、源范围、哈希与核心/上下文范围。
- 完整覆盖检查，禁止静默截断。
- 独立任务目录与可恢复清单。

此时即使串行调用读取者，也已经比一次读全剧更可控。

### 第二阶段：并行读取与统一归并

- 先以有限并发提取局部事实。
- 归并临时身份，记录事件和状态变化。
- 明确未知与冲突，不让多个 worker 直接写全局状态。
- 按事件链发布有限大小的上下文包。

### 第三阶段：独立核验与正文组装

- 每个核心范围执行原文忠实性核验。
- 全部相邻边界执行对接检查。
- 显式跨集依赖逐条核对。
- 对未经 worker 标记的潜在遗漏，补充原文扫描与分层覆盖审核。
- 合并为正式 outline/script，执行现有校验。

### 第四阶段：根据真实结果优化

只有基准显示需要时，才增加更精确的依赖失效、语义检索、第二模型或更复杂的时间关系表达。

不首发图数据库、向量服务、多代理辩论、长期常驻角色或自动无限修复循环。

## 12. 怎么证明它比当前方案更好？

### 12.1 分开测试工程正确性和模型质量

**离线确定性测试：**

- 中文/英文集标题与场次格式。
- 缺标题、缺集、重复集号、超长场。
- CRLF、Unicode、多字节字符边界。
- 核心范围无遗漏无重叠，上下文重复不计正文重复。
- 同一句台词多次出现不被误去重。
- 引文匹配、越界、错源哈希。
- 乱序完成、重复提交、输出截断、失败后恢复。
- 多 worker 不覆盖同一正式文件。
- 旧批准与当前输入不一致时失效。
- 新增此前未知别名或依赖后，保守失效策略有效。
- 正式辅助文件不破坏现有自动发现与独立复制运行。

**真实模型评估：**

使用用户允许的剧本或本仓库新写的独立故事。先定义故事和人工核验答案，再制作分块，不借用兄弟 skill 的样例。

至少覆盖：

- 跨多个批次的别名与身份揭晓。
- 同名不同人、同款不同物件。
- 闪回、并行线和故事时间未知。
- 人物撒谎、猜测、转述与真实获知。
- 道具交接、损坏、状态恢复。
- 长距离伏笔与最终回收。
- 原文确实矛盾，以及材料确实不完整。
- 中部关键事件，防止只记开头和结尾。
- 故意保留跨集关系两端的原文与局部事件，却删除中间依赖记录及 worker 的补读请求，检查审核能否主动发现遗漏关联。预期答案由独立人工基准决定，不能由被测系统自己的依赖清单决定。

最后一项区分“验证已经发现的依赖”与“发现尚未登记的依赖”。局部记录全部正确，并不意味着全剧关系已经完整。

### 12.2 对照方案

在模型、原文和大致预算可比时，比较：

A. 当前指南下的单会话分批阅读。

B. 各块独立摘要后直接合并。

C. 本文的来源事实、统一归并和依赖包方案。

D. 在 C 上增加独立审核，测量其净收益，而非预设审核必然更好。

可追加去掉远距离检索、只传上一集摘要等消融，用来判断哪一部分真正必要。

### 12.3 观察指标

- 有依据的重要事实是否被保留。
- 无依据断言与错误身份合并。
- 跨集状态、时间、知情范围和揭晓顺序错误。
- 已知缺失是否被诚实标记。
- 重要内容遗漏与引文错配。
- 审核发现的真实错误、误报，以及错误被“修复”为新错误的情况。
- 总输入/输出、实际调用次数、耗时和成本。

这些是一次性实验报告的指标，不建设永久评分系统或门失败累计统计。

审核模型不能给自己的方案打分作为唯一证据。至少对小规模基准进行人工逐条核验。没有真实剧本与模型评估前，不承诺准确率或节省比例。

## 13. 还需要用户确认什么？

不影响本份参考文档成立，但会影响实施参数：

1. **原文格式**：主要是 TXT/Markdown，还是 DOCX/PDF？后两者需增加提取与页码/文本映射，不能把 OCR 错误误认成剧情问题。
2. **典型规模**：总集数、每集长度、最长场次，以及常见的非线性叙事程度。
3. **script 权限**：仅忠实结构化，还是允许明确授权后的改写？改写后需额外区分源事实与修订事实。
4. **质量与成本优先级**：可接受的时延、模型选择和人工确认次数。

在这些数据未确定前，优先选择小批次、有限并发、完整来源覆盖和保守失效，不预先固定“每集一个 agent”或“一次十集”。

## 15. 最终建议

**先建立“原文可回查、局部有覆盖、跨集有依赖、修改会失效”的最小协议，再增加并发。**

subagent 的价值是把细读放入干净的上下文。统一事实的价值是让不同上下文共享同一套依据。独立审核的价值是从原文和跨集关系反证结果。

三者缺一，都会留下问题：只有分块会割裂，只有共享摘要会漂移，只有最终审核会再次遇到长上下文瓶颈。
