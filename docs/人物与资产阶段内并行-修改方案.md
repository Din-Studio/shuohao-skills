# 人物与资产阶段内并行：修改方案

状态：**已实施并验证**（mint-characters 4.2.0、mint-art 4.2.0；cast／art schemaVersion 1 不变）。两个阶段离线测试、全仓独立复制回归及独立代码审查通过；Demo 两集的隔离多代理提取、整理、来源核验与阶段间身份交接实测通过。验证仅覆盖本次局部身份范围，不含生图、全剧完整性或全项目批准。详情见 [实施验收](人物与资产阶段内并行-实施验收.md)。

适用范围：`skills/mint-characters/` 与 `skills/mint-art/`。完整流程仍为 **outline → characters → art → script → creation**，阶段之间的依赖不变。**阶段内部通过独立 subagent 并行执行，是本方案的核心原则，不以串行实测是否退化作为实施前提。**

历史实现见 [人物与资产分批解析：修改方案](人物与资产分批解析-修改方案.md)。该文记录 4.1.0 的串行接力，已经由本文对应的实现替代。现行执行细则以两个 skill 各自的 SKILL.md 与 references/dispatch.md 为准，本文记录设计依据、实施范围及验收要求。

## 一、问题与目标

characters 和 art 都需要独立读取原剧本。outline 只能提供故事背景，不能代替人物、地点和物件的原文证据。

调整前的首次识别采用串行接力：后一批读取本批原文和上一份累计草稿。它避免了每批重新通读前文，但仍有以下风险：

- 累计草稿持续增长，后面的模型需要同时处理更多身份、引用、事实和疑点。
- 前批判断可能成为后批默认接受的事实，错误归并可能继续传播。
- 小体量输入允许当前会话通读，体量阈值不能保证注意力充分。
- 核验者按身份或资产回读全部出处，没有累计原文读取上限。
- 无法独立派发时允许回退到同一会话，失去上下文隔离和独立核验。

这些是根据流程定义识别的风险，不是本次长剧本实测结论。不能据此声称现有结果一定遗漏或错误。

本方案的目标：

1. 原文阅读由独立 subagent 分批并行完成。
2. 不让一个调用同时承担全剧阅读、跨集身份判断和视觉设计。
3. 保持全剧身份一致、来源可追溯、已有 ID 稳定。
4. 通过独立核验发现遗漏和错误，不把覆盖声明当作理解证明。
5. 只增加必要职责，不建立新的调度系统或第二套资产协议。

## 二、第一性原理与取舍

### 2.1 三项必要工作

人物和资产整理的本质只有三项：

- 从原文获取事实。
- 判断不同位置描述的是否为同一对象。
- 形成一致的正式产物。

原文事实适合按批并行获取。跨批身份需要统一视角。正式产物需要唯一写者。独立核验用于检查前两项的结果。

因此采用：

> **并行阅读提取 → 一个 subagent 统一整理 → 并行独立核验 → 定向修复 → 正式发布。设计继续并行。**

并行本身不能保证可靠性。真正控制上下文负担的是独立调用、输入范围限制和职责分离。

### 2.2 删除不必要的设计

| 不采用的设计 | 原因 | 最小替代 |
| --- | --- | --- |
| 独立的精简候选索引层 | 多一次信息转换和一致性维护，压缩还可能丢失依据 | 整理者直接读取简洁、有出处的批次提取结果 |
| 默认多组归并和多级归并 | 分组之间仍可能有关联，最终还要再次统一 | 默认一个整理者；实际出现容量问题后再定向拆解 |
| 常设身份连接、漏登记、全局审核等多层角色 | 职责和材料重复，流程成本高 | 按批核验同时检查遗漏、事实和相关归并结论 |
| 第二套永久身份、注册表和生命周期 | 与正式 C/S/P 身份形成重复权威 | 工作文件仅供引用；正式身份仍由现有契约维护 |
| 自动相似度归并 | 名称、职业、外观相似不能证明同一对象 | 模型依据可定位的原文证据判断，未知保持未知 |
| 通用调度服务和自动重试系统 | 不是实现独立并行的必要条件 | 任务简报、现有工具和定向修复 |

## 三、最小工作流程

```text
主会话：登记来源、确定批次和读取范围
                    ↓
提取 subagent × N：按批并行读取原文，分别写提取结果
                    ↓
整理 subagent × 1：读取全部批次结果，统一人物／资产草稿
                    ↓
核验 subagent × N：按批并行对照原文检查草稿
                    ↓
整理者：根据具体问题定向修复；受影响批次独立复核
                    ↓
主会话：执行确定性校验、记录有依据的审核、正式发布
                    ↓
设计 subagent × N：分组并行设计，apply-designs 统一写回
                    ↓
按现有媒体交接生成图片、核验媒体、渲染报告
```

阶段内部必须并行，不等于所有步骤都必须并行。统一身份和统一写入存在依赖，保留单一整理者更简单。

并发数量由运行资源决定，不要求所有批次同时启动。不能将一次只派一个、逐批等待的串行接力称为并行。

单集输入也使用独立 subagent。可以并行安排不同关注点的提取任务，例如 characters 的出场／发声与提及／别名，art 的地点与物件，再由整理者统一。它们可以读取同一集，但不能互相自证；后续核验仍由独立调用执行。不要为满足并发而任意切断无法独立理解的原文。

## 四、读取范围和上下文约束

### 4.1 基础规则

- **主会话不读取原文正文。** 不先通读再派发，也不在修复时替代来源任务。
- **每个 subagent 一次调用累计最多接触四个不同集号的原文。** 完整阅读、检索命中、前情和定向回读全部计入。
- 每批一至四集。四集是上限，不是安全保证；长集、对白密集、对象多时继续缩小。
- 同一调用不能接着处理下一批，分块或改换任务名称不重置累计范围。
- 没有 subagent 工具时，通过独立进程执行。两者都不可用时停止，不回退到主会话通读，不声称独立核验完成。
- 原文读取和工作材料读取都要控制体量。限制集数不代表累计提取结果可以无限增长。

例如，一个调用已经读取第九至十二集，再需要第二集证据，应另派任务，不因“只读取几行”而突破上限。

### 4.2 长集与单文件多集

极长单集可以按可靠场次或行范围拆分独立任务，必要时保留边界重叠。四集上限不能成为一次读取超长单集的理由。

单文件包含多集时，派发明确的集号、路径和行范围，不把整个文件直接交给每个任务。无法可靠确定边界时先确认来源范围，不猜测后通读全文。

### 4.3 程序读取与模型阅读不同

来源登记、摘要和行数检查可以在程序内读取全部文件字节，但不应把全文输出到主会话。

程序读过文件、生成分块或通过 coverage 检查，都不能证明模型已理解原文。coverage 只记录实际阅读范围的声明，语义可靠性仍需独立核验。

## 五、职责与文件边界

### 5.1 主会话

负责来源登记、分批、派发、执行确定性命令和向用户汇报。

- 给出负责集号、文件绝对路径、行范围、输出位置和必要指南。
- 不接受整段原文或全部提取正文回贴；任务只回报文件路径、状态及具体阻断。
- 正式文件只有主会话发布，设计通过现有 `apply-designs` 统一写回。
- 不凭结构通过自动填写语义确认，不把待核验结果交给下游作为已确认身份。

### 5.2 提取者

只读取本批原文，不读取前面所有批次的累计草稿，不制作视觉设计，不分配最终 C/S/P ID。

每批一份简洁工作记录，至少能定位对象、事实、来源和疑点。可以使用文件内临时条目标识便于引用，但不建立第二套永久身份或生命周期。

允许局部结果重复。宁可留下待归并条目，也不能为了整洁而猜测跨集身份。本批内部有明确证据时可以判断同一对象，但要保存证据和揭晓位置。

### 5.3 整理者

默认只有一个，主要读取各批提取结果，不通读全剧原文。

- 对跨批条目判断确认同一、确认不同或尚不能确认。
- 合并有证据的重复条目，保留未知与冲突。
- 保留原文揭晓顺序、人物知识边界和状态链，不用后文身份抹去前文的不知情状态。
- 形成一份符合现行正式契约的候选草稿。
- 必要时按需求读取特定集数、特定行范围；累计最多四集。超出范围的证据需求另派任务。
- 核验期间不修改草稿，收到结论后再统一修复。

所有提取结果仍可能超出单个调用的合理容量。发生这种情况时，报告具体材料范围，按实际疑点派发证据或局部整理任务；不要回退到阅读全剧，也不要预先建立多级索引和归并架构。

### 5.4 核验者

按批独立派发，并行检查本批原文、草稿中相关条目及必要归并依据。不读取提取者的自我评价作为核验依据，不修改草稿。

核验必须检查两个方向：

| 方向 | 检查内容 |
| --- | --- |
| 原文到草稿 | 对象是否遗漏，称谓、身份限制、物件交接和状态是否丢失 |
| 草稿到原文 | 结论是否有证据，是否错误合并／拆分，是否提前揭晓、补写未知或把人物说法当成事实 |

漏登记检查按批完整覆盖，不只由一个任务抽查全剧。跨批关系不能仅凭本批原文就宣布通过：应检查相关提取结果和归并依据，必要时在读取上限内定向回读，或明确提出独立证据需求。

贯穿全剧的主角或核心场景也按批检查来源，不要求一个核验者回读其全部出处。针对跨批身份的争议，另派具体证据任务，不默认增加常设审核层。

### 5.5 修复与复核

核验结论给出具体对象、问题、来源位置和建议修正范围。整理者集中修复草稿，避免多个任务同时修改同一文件。

- 原文事实修复后，复核受影响批次。
- 合并、拆分或关系变化影响多个批次时，相关批次均需复核，不能只检查最先提出问题的一批。
- 无法解决的问题保留未知或阻断对应交付，不通过删除对象、修改预算或虚构解释消除问题。
- 不新增失败累积日志或统计，不建立通用自动重试系统。

### 5.6 设计者

身份和来源通过核验后再设计。读取负责对象的已确认事实、限制、必要出处和适用 production，不接收全剧原文和全部审核过程。

- 易混淆人物可以同组，便于区分外观。
- 基准场景与其变体同组，强关联道具尽量协调。
- 每人只写自己的设计文件，不修改身份字段和正式产物。
- 原文回读仍受每次调用累计四集上限约束。
- 设计并行不改变媒体依赖。需要基准图的变体，不能在基准图生成和核验前冒充完成。

## 六、两个阶段的内容差异

### 6.1 characters

提取重点：

- 原文称呼、别名及各自出处。
- 出场、发声、仅被提及等出现方式。
- 无台词人物、匿名声音、群体和非人主体。
- 明确身份关系、身份揭晓位置、未知和限制。

整理重点：同人、同名不同人、别名、匿名身份和跨集关系。名称或职业相同不能自动合并；不能为满足角色预算减少真实身份。

示意：一批登记“夜班员”，另一批登记“许禾”。提取者各自保留事实；整理者根据明确证据判断是否同人，没有足够证据就保持分开和疑点。

首次生成时，先完成归并和来源核验，再由唯一写者构成候选 cast，使用现有 reconcile 分配 C ID。工作条目不是正式人物身份。

### 6.2 art

提取重点：

- 地点称呼、空间结构、标志物和空间关系。
- 物件称呼、材质、标记和其他可区分特征。
- 拿取、交接、持有、破损、修复及内容变化。
- 光照或空间状态变化、来源和身份疑点。

整理时依次区分：

1. 是否同一地点或实物。
2. 是否需要独立美术资产。
3. 是否需要视觉变体或状态图。

同一铁盒的交接、腾空通常是状态事实，不自动建立多个道具。场次不同不等于地点不同，情绪变化不等于视觉变体；变体继续依据光照或空间状态及制作需求判断。

局部提取不自行执行 register 分配正式 S/P ID。归并后由唯一写者使用现有登记与确认流程建立正式草稿，不新增全局重新编号机制。

人物关联只引用已确认 cast。无法对应 C ID 时，提出具体问题交由 characters 定向核验；art 不按名称重新判断人物身份。

## 七、阶段关系、稳定 ID 与正式契约

- 完整流程仍为 outline → characters → art → script → creation。characters 完成本次范围和交接后，art 才进入该范围；不因阶段内并行而绕过人物身份依赖。
- 首次提取中的重复条目允许存在，正式身份只能有一份权威。
- 已有 cast/art 的增量工作同样按涉及范围独立派发和核验，但沿用原有 ID、identityKey、注册表和预算。
- 已发布身份的合并、拆分、删除和纠正继续按现有生命周期记录，不重新登记全剧或重新编号。
- 身份、来源和设计变化后，重新核验实际受影响的参考图、工作单和下游映射；不把 ID 沿用当成审核沿用。
- 若正式字段及含义不变，继续使用当前 cast v1、art v1。工作记录放在各自 `.work/`，不增加第二种正式格式，不引入旧版读取或兼容分支。
- 两个 skill 各自包含完整派发说明和必要实现，不能依赖兄弟 skill 的脚本或指南才能运行。

## 八、实施范围

优先修改流程文档，不预先新增调度代码：

| 位置 | 预期调整 |
| --- | --- |
| 两个 skill 的 `SKILL.md` | 取消小体量当前会话通读和串行接力分流，明确阶段内独立并行及交接顺序 |
| 两个 skill 的 `references/dispatch.md` | 改为提取、整理、核验三种职责，明确读取范围、唯一写者和不可回退规则 |
| characters 的 `references/roster-pass.md` | 局部提取与跨批身份整理分离，不读取累计草稿接力 |
| art 的 `references/lifecycle.md` | 去除接力者逐批登记身份的约定，保留现有稳定 ID 与发布后变更规则 |
| 相关来源说明、双语 README、CHANGELOG 与测试 | 与最终实施同步，不留下相互冲突的现行规则 |

现有 seed、reconcile、register、validate、identity-inputs、apply-designs 和媒体交接优先复用。实施时检查现有命令的实际能力，不把本文描述当作已有新命令。

只有确定性操作确实重复且容易出错时，才增加小型辅助，例如输出批次元数据或检查结果来源范围。代码不自动理解原文、不判断同人同物，也不能靠读取范围声明审计实际工具历史。

不新增调度服务、数据库、文件锁、通用身份关系图、自动相似度归并、第二套正式资产格式、默认多级归并或失败累积日志。

## 九、验收与验证边界

### 9.1 流程验收

- 多集原文提取和按批核验确实通过独立 subagent 并行派发，而不是串行接力。
- 单集输入也存在独立 subagent 并行工作，核验不由提取者自我完成。
- 每次调用的累计原文接触不超过四集，长集按实际体量缩小范围。
- 主会话不读取原文；整理者主要读取提取结果，只在必要时按范围回读。
- 各批结果没有被要求接受前批累计草稿，工作记录不提前分配正式 ID。
- 核验覆盖本批全部原文，既检查遗漏，也检查草稿结论；跨批证据不足明确提出问题。
- 同一时刻草稿只有一个写者，正式产物只有主会话发布。
- 无法独立派发时停止，不回退到主会话完成。

### 9.2 语义与现有行为回归

各 skill 使用自己的样例，至少覆盖：

- characters：跨批别名、同名不同人、匿名身份未确认、无台词／仅出声／仅提及、身份揭晓顺序。
- art：跨批同地同物、交接和状态链、场景变体、未建资产线索、carrierRefs 的人物权威。
- 整理者错误合并或遗漏后，独立核验能提出有来源的具体问题。
- 增量修改保持既有 ID，变更和预算仍遵守现有契约。
- 设计写回、来源核验、正式校验和独立复制运行不回归。

离线测试只能证明确定性规则和静态约定。真实并行派发、上下文隔离及原文忠实度，需要通过实际多代理执行和内容复核验证，未执行时明确标记“未验证”。不以结构通过、摘要匹配或 coverage 完整冒充语义通过。

## 十、成本、限制与最终决定

必要成本包括：局部提取可能产生重复条目、增加一次统一整理调用、独立核验重新阅读原文。这些成本分别用于避免局部猜测、统一跨批身份和发现错误。

本方案不保证模型绝不遗漏，也不保证一个整理者永远能够处理任意规模。出现实际容量问题后，按具体材料和疑点缩小任务，不提前建设尚无必要的复杂系统。

最终采用的最小原则是：

> **原文按批并行读取，结果由一个 subagent 统一整理，再按批并行独立核验。设计继续并行。先解决上下文隔离和来源核验，不预先建设超大规模调度系统。**
