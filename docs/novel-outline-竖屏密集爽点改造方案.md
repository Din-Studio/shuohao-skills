# novel-outline 竖屏密集爽点改造方案

- 状态：待实施。本文件只定义修改方案，不代表功能已经完成。
- 基线：仓库 `a499e1b`，当前 `novel-outline` 版本为 1.5.0。
- 目标：把大纲从“改编说明与资产规划”调整为“可兑现、可追踪、可向剧本传递的短剧叙事计划”。
- 范围：以 `novel-outline` 为主，包含必要的 `novel-script` 接口升级及美术、创作、合并报告的接入检查。
- 非目标：不承诺爆款，不生成分镜，不调用付费模型，不建设投放分析系统，不新增质量门失败累积日志或统计功能。

## 1. 核心决策

1. 保留 JSON、Markdown、HTML 三类交付。JSON 是唯一编辑源，其他两者由脚本重新生成。
2. 区分开场吸引、过程施压、剧情转折、情绪兑现和集尾悬念，不再把它们全部计为爽点。
3. 每集必须产生局势变化。密集爽点模式下，每集至少一次兑现，但不把字段齐全等同于观众真的获得满足。
4. 保留全剧统一 `beats` 表。节点所属集数只存于 `beats[].episode`，不在分集重复保存节点编号列表。
5. 开场和集尾改为事件表达。悬念通过编号连接后续解决事件。
6. 大纲不填写机位拆解。一次性场景不再因为缺少复用方案而阻断交付。
7. 增加故事驱动和阶段兑现，避免“每集都有反击，全剧却没有进展”。
8. 使用显式版本边界。新版大纲与新版剧本采用 `schemaVersion: 2`，不把旧数据静默解释成新版。
9. 自动校验只证明字段、引用、顺序、覆盖和计划满足约束。内容有效性单独评审。
10. 新样例先确定故事，再确定节奏，不借用兄弟 skill 的故事，不提前生成分镜或图片。

## 2. 当前问题及依据

### 2.1 已确认的问题

| 当前实现 | 问题 | 修改方向 |
| --- | --- | --- |
| `episode-pass.md` 把 `hook` 定义为让观众点击下一集的问题 | 与 `suspense` 重叠；下游剧本却把它当作开场 | 改成 `opening` 与结构化 `cliffhanger` |
| `maxBeatGap` 默认 3，按集号计算 | 不检查集内节奏；两分钟单集下，相邻节点所在集号可相隔六分钟 | 每集兑现覆盖＋集内位置＋阶段兑现 |
| 大爆点只要求早于最后一集 | 60 集首次大爆点在第 59 集也能通过该检查 | 首次大兑现期限及阶段最大间隔 |
| `beats[].type` 是自由文本，所有节点参与爽点统计 | “悬念钩”“收束”可以冒充兑现 | 增加 `kind`，只对 `payoff` 计算兑现密度 |
| 三名角色出场就要求 `crowdPlan` | 出场不等于同框，且大纲被迫决定机位 | 删除该字段及对应硬门 |
| 一次性场景必须有 `reusePlan` | 先强制生产复用，再决定叙事是否需要 | 改为提示，复用方案可选 |
| 每集只检查三段文本非空 | 不能表达该集带来的局势变化 | 增加 `stateChange` |
| 悬念没有解决事件引用 | 无法区分有意延迟和遗忘 | 集尾悬念编号＋`beats[].resolves` |
| 剧本 `beatsClaimed` 按 `type` 去重 | 同集两个同类兑现可以被一次文字认领覆盖 | 改为按节点 ID 认领具体剧本节拍范围 |

### 2.2 不应误删的内容

- `characters[].from` 是角色来源追踪；`adaptation.merge` 是改编决策。两者相关，但并非同一职责。
- `synopsis` 是分集叙事上下文；`beats` 是重要事件的结构化契约。保留两者，但内容评审必须核对一致性。
- 角色、场景、道具引用用于下游生产和资产汇总，不因强调爽点而删除。
- JSON、Markdown、HTML 是数据与视图的分工，不是三份独立故事版本。
- 自动资产清单继续由脚本计算，不增加可手写的顶层 `assets`。

## 3. 交付物与职责边界

目录保持不变：

```text
<工作目录>/
├── production.json
└── outline/
    ├── <书名>-outline.json
    ├── <书名>-outline.md
    ├── outline-report.html
    └── .work/
```

- JSON：故事、改编取舍、角色、场景、道具、剧情节点、分集计划。
- Markdown：完整阅读版，优先展示故事承诺和分集兑现。
- HTML：评审版，优先展示兑现覆盖、阶段升级、悬念解决关系。
- `.work/`：临时摘要、批次草稿、内容评审意见。可删除，不成为下游依赖。
- 渲染 HTML 不进入版本控制。

职责边界：

| 层级 | 本次职责 |
| --- | --- |
| outline | 谁想得到什么、受到什么阻碍、每集发生什么变化、何时兑现 |
| characters | 人物外观、性格表现、声音与一致性资料 |
| art | 场景和道具外观、状态变体、资产复用 |
| script | 动作、台词、场次、估算时长、节点在实际剧本中的位置 |
| creation | 镜头、竖屏构图、多人同框拆解、生成提示词和参考图挂载 |

画幅继续由 `production.json` 管理。大纲不再保存一份 `aspectRatio`。

## 4. outline.json v2 字段契约

以下“必填”指完整交付阶段。骨架阶段的差异见第 7 节。

### 4.1 顶层结构

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `schemaVersion` | 必填，整数 2 | 与 skill 软件版本分开 |
| `source` | 必填 | 原作或原创故事名称 |
| `lang` | 可选 | 保持原有界面语言继承规则 |
| `params` | 必填 | 集数、时长、题材、改编模式、阈值和节奏策略 |
| `story` | 必填，新增 | 全剧情绪承诺、主线驱动和终局兑现 |
| `adaptation` | 必填 | 改编取舍和风险 |
| `characters` | 必填 | 角色清单及来源 |
| `scenes` | 必填 | 场景清单 |
| `props` | 可选 | 叙事道具清单 |
| `arcs` | 可选，新增 | 长剧的阶段目标和阶段兑现 |
| `beats` | 必填 | 统一剧情节点表 |
| `episodes` | 必填 | 连续编号的分集计划 |

不增加总分、爆款概率、失败历史、模型自评分等字段。

### 4.2 params：保留生产目标，增加节奏参数

保留：`episodes`、`minutesPerEpisode`、`genre`、`adaptMode`、`preferences`。

`params.thresholds` 只保留资产数量限制：

- `maxLeads`，默认 5。
- `maxSupport`，默认 10。
- `maxFunctional`，默认 10。
- `maxPrimaryScenes`，保持当前按总集数计算的默认值。
- `maxProps`，默认 8。

删除 `maxBeatGap`。旧节点间隔不能直接换算为新兑现密度。

新增 `params.pacing`，可省略；省略时采用以下默认值：

| 字段 | 默认值 | 类型与用途 |
| --- | --- | --- |
| `minPayoffsPerEpisode` | 1 | 正整数；每集兑现节点数下限 |
| `firstMajorByEpisode` | 3 | 正整数；首次大兑现的最晚集数，实际期限取它与总集数的较小值 |
| `maxMajorGap` | 5 | 正整数；相邻大兑现所在集号的最大差 |
| `defaultResolveWithin` | 2 | 正整数；集尾悬念默认在后续两集内解决 |

所有参数要求有限正整数，不接受字符串、零、负数或小数。显式提高阈值属于创作决策，报告须显示实际生效值，不把调整后的通过包装成默认策略通过。

不在 outline 增加“开场必须几秒”的硬阈值。大纲没有实际台词和镜头，不能证明秒级节奏。

### 4.3 story：全剧驱动

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `protagonistId` | 必填 | 指向 `characters` 中的主角组成员；确定主要叙事视角，不禁止其他主角 |
| `goal` | 必填 | 主角贯穿全剧的具体目标 |
| `opposition` | 必填 | 阻止目标实现的人、制度或现实条件 |
| `stakes` | 必填 | 失败将失去什么 |
| `emotionalPromise` | 必填 | 观众持续期待的满足，例如夺回尊严、被坚定选择、揭穿骗局 |
| `ending` | 必填 | 主线及情绪承诺最后如何完成；不是逐镜描写 |
| `endingBeatId` | 必填 | 指向最终集中的 `kind=payoff`、`weight=major` 节点 |

`ending` 解释整体意义，最终节点的 `outcome` 描述具体事件。两者不应复制同一句话凑字段。

本版面向一个完整交付的故事段落。续作可以在叙事中保留余味，但不允许用未解决的主线替代本季兑现。

### 4.4 adaptation：去除重复核心，保留取舍

- 删除 `adaptation.core`，核心叙事迁入 `story`。
- `keep[]`、`cut[]`、`merge[]`、`risks[]` 保留。
- `keep` 至少一条；关键保留项附原文证据；非忠实模式仍须解释删除项。
- `cutNote`、`mergeNote` 保留为可选的决策补注，不再由流程强制填写。
- `what/why/evidence` 和 `what/plan` 的现有结构保持。
- 来源不足时明确限制，不凭书名补全原作。

### 4.5 characters、scenes、props：保持下游稳定

人物字段保持：`id`、`name`、`role`、`tier`、`arc`、`from`。主角组和重要配角仍须填写人物弧。

场景字段保持：`id`、`name`、`primary`。`reusePlan` 改为可选建议：

- 单次出现不再触发失败。
- 资产报告仍可提示“仅出现一集，建议评估制作投入”。
- 有建议时，美术 seed 继续作为提示搬运，不直接替美术决定变体结构。

道具字段保持：`id`、`name`、`function`、可选 `beatIds`。

`props[].beatIds` 在 v2 中可以引用任意剧情节点，不限于兑现。物证也可能制造危机或转折。文案从“托起哪个爽点”调整为“在哪个关键事件中承担作用”。

### 4.6 beats：统一剧情节点表

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `id` | 必填 | `B` 加至少两位数字，唯一；保留稳定编号 |
| `episode` | 必填 | 1 至总集数的整数，是节点所属集的唯一来源 |
| `position` | 必填 | `opening`、`early`、`middle`、`late`、`ending` |
| `kind` | 必填 | `pressure`、`turn`、`payoff` |
| `type` | 必填 | 题材化标签，例如公开平反、关系确认、身份揭破 |
| `weight` | 兑现必填 | `kind=payoff` 时只能为 `minor/major`；其他类型禁止填写 |
| `setup` | 必填 | 事件所承接的冲突、铺垫或期待 |
| `outcome` | 必填 | 实际发生的事件及后果，替代旧 `payoff` 文本字段 |
| `resolves` | 可选 | 被本事件解决的集尾悬念 ID 数组，无重复 |

分类定义：

- `pressure`：提高阻力、代价或紧迫性，不计为兑现。
- `turn`：改变信息、判断或局势方向，不自动计为兑现。
- `payoff`：兑现先前期待，给出可识别的情绪或利益结果。

`major` 的含义是阶段性改变主线目标、权力关系或关键人物关系，不是作者声称“很震撼”。是否真的达到这个程度由内容评审判断。

顺序规则：

1. 数组按集号、位置枚举顺序排列。
2. 同集同位置可以有多个节点，数组中的先后就是叙事顺序；不增加重复的 `order` 字段。
3. 不允许用同一事件的两个近义表述重复计数。脚本可提示完全相同的 `outcome`，语义重复由内容评审判断。
4. 一个事件同时产生转折和兑现时，优先记为一个 `payoff`，通过 `type` 和 `outcome` 说明转折，不拆成两个节点虚增密度。
5. 只有 `kind=payoff` 进入兑现数量统计。所有类型均可解决悬念。
6. `position` 是粗略叙事区段，不声称代表精确秒数或等长五等分。

### 4.7 episodes：开场、推进、变化与集尾

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `ep` | 必填 | 1 起连续编号，数量等于总集数 |
| `opening` | 必填 | 开场直接发生的事件，不是抽象提问 |
| `synopsis` | 必填 | 本集行动、冲突与因果过程，包含本集节点的实际发生 |
| `stateChange.before` | 必填 | 本集开始时与主线有关的处境 |
| `stateChange.after` | 必填 | 本集结束时发生的实质变化 |
| `cliffhanger` | 必填 | 非最终集为对象；最终集固定为 `null` |
| `sceneIds` | 必填 | 引用场景，保持原规则 |
| `characterIds` | 必填 | 引用角色，保持原规则 |
| `propIds` | 可选 | 引用叙事道具 |
| `warnings` | 可选 | 制作风险提醒，不作为叙事质量替代品 |

删除 `hook`、`suspense`、`crowdPlan`。v2 不允许新旧字段同时存在。

`stateChange` 不另设主角行为字段。主角采取的行动写入梗概，评审检查行动与结果之间的因果，避免为了“检查主动性”再重复描述一次。

分集不增加 `beatIds`。报告通过 `beats[].episode` 汇总本集节点。

叙述体限制覆盖 `opening`、`synopsis`、状态变化、悬念事件和节点文本，不填写剧本对白。原文证据 `evidence` 不参与此限制。

### 4.8 cliffhanger：有限期的追看承诺

非最终集结构：

```json
{
  "id": "Q01",
  "event": "胜诉消息刚发布，对方出示一份盖着女主签名的授权书。",
  "question": "这份授权书能否推翻刚取得的胜利？",
  "dueByEp": 3
}
```

- `id`：`Q` 加至少两位数字，全剧唯一。
- `event`：具体发生的事件，必填。
- `question`：这个事件让观众等待的答案，必填。它不是另一份集尾事件。
- `dueByEp`：可选；省略时为 `min(ep + defaultResolveWithin, 总集数)`。
- 显式期限必须满足 `ep < dueByEp <= 总集数`。
- 完整交付时，每个 Q 必须恰好由一个后续节点的 `resolves` 引用。
- 解决节点所属集必须大于提出集，且不晚于期限。
- 一个节点可以解决多个 Q；同一 Q 不允许被重复声明解决。
- 如果只揭示部分答案，应把本次可回答的问题写窄。解决后产生的新问题使用新的 Q，不靠反复标注“已解决”掩盖拖延。
- 最终集 `cliffhanger=null`。最终集的余味写在梗概中，不强制制造新的追更债务。

只追踪每集的主要集尾悬念，不为所有伏笔建立数据库。长期情绪承诺由 `story` 和可选 `arcs` 管理。

### 4.9 arcs：可选的阶段推进

适用于较长故事；短篇无需为满足结构机械添加。

| 字段 | 说明 |
| --- | --- |
| `id` | `A` 加至少两位数字，唯一 |
| `startEp` / `endEp` | 阶段起止集数，均包含边界 |
| `goal` | 该阶段主角要完成的目标 |
| `payoffBeatId` | 该阶段结束集中的大兑现节点 |

如果提供 `arcs`：

- 按起始集排序，连续、无重叠地覆盖完整集数。
- 每个阶段的 `payoffBeatId` 必须指向 `endEp` 的大兑现。
- 阶段目标如何升级由内容评审检查，不用字符串差异冒充升级。
- 阶段终点由节点的 `outcome` 描述，不再增加重复的 `payoffText`。

## 5. 节奏策略及计算定义

### 5.1 默认硬约束

设总集数为 N，兑现节点定义为 `kind=payoff`，大兑现还要求 `weight=major`。

1. 每集兑现数至少为 `minPayoffsPerEpisode`。
2. 首次大兑现集号不晚于 `min(firstMajorByEpisode, N)`。
3. 将大兑现所在集号去重排序，相邻差值不超过 `maxMajorGap`。
4. `story.endingBeatId` 必须落在第 N 集且是大兑现，因此尾段也受大兑现间隔约束。
5. 每个非最终集有主要集尾悬念；所有悬念按期限解决。
6. 所有分集都有状态变化和开场事件。

说明：`maxMajorGap=5` 表示大兑现可以出现在第 3、8、13 集；不是允许五个完整空白集。规则按集号计算，不伪称秒级密度。

单集作品：不需要集尾悬念，最终兑现同时满足首次大兑现。双集作品：第一集至少有小兑现，第二集可完成首次大兑现。

### 5.2 默认软目标

以下仅用于写作建议和当前报告提示，不作为虚假的通用爆款公式：

| 单集时长 | 建议 |
| --- | --- |
| 不超过 60 秒 | 一个完整的小兑现通常比堆砌多个标签更重要 |
| 90–120 秒 | 争取 2–4 次有效推进；两次小兑现或一次完整大兑现 |
| 超过 120 秒 | 根据实际剧本检查空转段，不仅按分钟数线性堆节点 |

共同建议：

- 前 3–5 秒进入事件、冲突或后果。这是剧本和成片的验证目标，不是大纲已验证结果。
- 不连续多集只有受辱、误会和铺垫。
- 兑现之后产生更高一级的问题，而不是把本集承诺全部扣到下一集。
- 交替使用信息优势、关系变化、资源获得、公开认可、选择与牺牲等兑现方式。
- 允许悲剧、悬疑中的情绪释放，但不能把纯粹加重痛苦一律改名为兑现。

可参考但不强制的单集过程：危机承接 → 主角行动 → 小兑现 → 阻力升级 → 更大兑现 → 新问题。

### 5.3 竖屏叙事原则

- 每个重要节点有一个清楚的注意力中心。
- 关键事实尽量通过行为、证据、选择和后果表达。
- 不依赖观众同时理解大量人物、地点和背景关系。
- 角色数量限制管理全剧资产；单场注意力负担由剧本评审和视频创作处理。
- 不新增大纲机位、景别、画面坐标、镜头长度等字段。

## 6. 校验分层：硬规则、提示与内容评审

### 6.1 硬规则

保留原有字段类型、ID、角色分档、主场景数量、道具数量、引用完整和叙述体检查，按 v2 字段调整。

删除或替换：

| 旧门 | 新处理 |
| --- | --- |
| `once-scene` | 删除硬门，改为当前报告提示 |
| `crowd-plan` | 删除，大纲不验证拍摄方案 |
| `beat-gap` | 替换为每集兑现覆盖 |
| `ep1-hook` | 替换为所有分集开场事件字段检查 |
| `major-early` | 替换为首次期限、阶段间隔、终局兑现检查 |
| `ep-fields` | 检查新版分集字段及最终集例外 |
| `risk-flag` | 关键词扫描改为非阻断提示，不再把提到“雨”视为必须拍雨戏的证明 |

新增稳定门标识建议：

- `schema-version`：版本明确，旧新字段不混用。
- `story-contract`：主角引用及全剧驱动字段完整。
- `beat-contract`：节点分类、位置、强度规则、排序合法。
- `payoff-coverage`：每集至少一次兑现或满足用户提高的下限。
- `major-cadence`：首次大兑现和相邻大兑现间隔符合策略。
- `ending-payoff`：终局节点存在并位于最终集。
- `episode-state`：前后状态非空；完全相同文本拒绝，语义变化仍待评审。
- `cliff-resolution`：悬念身份、期限、唯一解决关系和时间顺序正确。
- `arc-contract`：有阶段划分时检查覆盖和阶段兑现。

不维持“恰好 14 道门”的宣传口径。实际门数由职责决定。

### 6.2 当前报告提示

只从当前 JSON 即时计算，不写累积历史：

- 只出现一次的场景。
- 检出的潜在生成风险。
- 90–120 秒单集只有一次小兑现。
- 所有兑现集中在同一粗略位置。
- 连续多集重复同一种兑现标签。
- 完全相同的节点结果文本。
- 用户显式放宽默认期限的悬念。

这些提示不是“剧情不好”的自动结论。

### 6.3 内容评审

新增仓库自己的 `references/story-review.md`，不依赖外部 skill。

必须逐项评审，并引用具体集号和节点 ID：

1. 观众为什么站在主角一侧？情绪承诺是否明确？
2. 主角采取了什么行动？结果是否来自行动与既有条件，而非凭空救援？
3. 标为兑现的事件，是否真的满足了已经建立的期待？
4. 大兑现是否改变局势，而非把同类冲突再重复一遍？
5. `synopsis` 是否真正包含本集节点？`opening` 是否与本集最前面的事件一致？
6. 集尾事件是否承接本集结果？后续节点是否真的回答对应问题？
7. `stateChange` 是否可见？删除该集是否会破坏后续因果？
8. 反转是否有此前材料支撑？是否靠强行变蠢或隐藏已知事实制造惊讶？
9. 相邻批次的证据、身份、关系和资源状态是否连续？
10. 终局是否兑现 `story.emotionalPromise`，而不是只解决形式上的事件？

评审意见写入当前工作记录或 `.work/`，修订后重跑校验；不新增永久评审评分库。最终汇报分别说明“结构校验结果”“内容评审是否执行”，渲染器不能自行声称内容评审通过。

## 7. 工作流调整

### 7.1 收集参数

保留集数、时长、题材、改编幅度和偏好。

增加创作确认项：观众主要期待哪一种满足。如果用户没有明确表达，由给定文本提出建议，不要求用户理解所有 JSON 字段。

自动驾驶模式继续从 `production.json` 读取。自动驾驶转移审批权，不取消结构检查或内容评审。

### 7.2 先定故事，再制作骨架

顺序调整为：

1. 确定 `story`：目标、阻力、代价、情绪承诺、结局。
2. 决定保留、删除和合并，完成角色清单。
3. 确定阶段大兑现和终局兑现，长剧按需填写 `arcs`。
4. 向每集分配小兑现、施压和转折，补齐粗略位置。
5. 根据已确定的事件登记场景和道具。
6. 完成快版骨架校验，交用户确认或在自动驾驶下记录决策。

用户确认的重点由“三件改编取舍”扩展为：

- 主角最终要赢得什么，观众为什么关心。
- 原作哪些内容被删除、哪些人物被合并。
- 第一轮和阶段性兑现落在哪些集。
- 终局是否兑现承诺。

### 7.3 分集写作及跨批次交接

每批最多 10 集的上限保持，但分批输入不再只有静态骨架：

- 完整故事驱动、角色与节点计划。
- 本批涉及的阶段目标。
- 上一集的 `stateChange.after`。
- 此前已提出、在本批或以后解决的悬念及其计划期限。
- 后续批次已经约定的解决节点。

批次之间默认顺序衔接。只有边界状态和跨批次悬念计划已经明确时才并发，不能无条件并发后再期待自动一致。

写入每集时核对：开场事件 → 主角行动与阻碍 → 本集兑现 → 状态变化 → 集尾问题。

### 7.4 分阶段校验

保留 `--stage skeleton|beats|full`，明确每个阶段的能力：

| 阶段 | 必须验证 | 明确跳过 |
| --- | --- | --- |
| `skeleton` | 参数、story 文本、人物场景道具、改编说明 | 尚未生成的节点引用和分集检查 |
| `beats` | skeleton 内容＋节点分类排序、每集兑现计划、阶段和终局节点引用 | 真实分集梗概、集尾 Q 完整解决关系、资产实际出场覆盖 |
| `full` | 全部契约、全部分集、悬念解决、资产实际引用 | 不把内容质量推断为脚本通过 |

`skeleton` 时 `endingBeatId` 可暂缺；`beats` 时必须存在。骨架节点的 `resolves` 可暂缺，完整分集写完后必须补齐。

只有完整校验通过才能按“完整大纲”交付。骨架通过只表示该阶段通过，不显示成全项通过。

### 7.5 内容评审与汇报

完整大纲形成后，执行第 6.3 节的内容评审，修改问题并重新校验。

最终汇报包含：

- 集数、时长、主要情绪承诺。
- 每集兑现覆盖、首次大兑现、阶段大兑现位置。
- 悬念是否全部按计划解决。
- 结构校验结果与内容评审执行情况。
- 自动驾驶下代用户作出的决策、材料限制和未验证项。
- JSON、Markdown、HTML 路径。

不使用“已经成为爆款”“自动验证剧情精彩”等表述。

## 8. 下游接入修改

### 8.1 novel-script：必须同步修改

这是本次唯一需要实质升级数据契约的下游。

新增剧本顶层 `schemaVersion: 2`。保留现有 `hook`、`cliff`、`hookBeat` 名称，以减少创作层无关字段迁移，但重新定义最终集收束：

| 大纲 v2 | 剧本 v2 seed 行为 |
| --- | --- |
| `episodes[].opening` | 填入 `hook` |
| 非最终集 `cliffhanger.event` | 填入 `cliff` |
| 最终集 `cliffhanger=null` | `cliff=null`；新增 `closure`，预填 `story.ending` |
| 非最终集 | `closure` 不填写 |
| 当集节点 | 填入待认领的 `beatClaims` |
| 单集分钟数 | 继续换算 `targetSeconds` |

剧本 v2 在不提供 outline 时也可独立校验：每集必须为“非空 cliff 且无 closure”或“cliff 为 null 且 closure 非空”之一。提供 outline 后必须与真正的最终集身份一致。缺少 outline 时，报告明确不能核对全剧终局身份。

删除按类型字符串认领的 `beatsClaimed`，改为：

```json
{
  "beatClaims": [
    {
      "beatId": "B03",
      "start": [1, 4],
      "end": [1, 8]
    }
  ]
}
```

- `start/end` 为 1 起始的 `[场次序号, 场内节拍序号]`，不是场景 ID。
- 所有当集大纲节点均需认领，包括施压和转折，不仅兑现。
- seed 只预填 `beatId`，范围留 `null`；未完成剧本校验应失败，不伪造真实落点。
- 编号必须存在、属于本集、不得重复；当集节点不得漏领。
- 范围端点必须存在，转换为全集节拍序号后 `start <= end`。
- 认领范围按大纲节点顺序排列，前一节点结束位置必须早于下一节点开始位置，避免同一段戏重复兑现。相关事件应在大纲阶段合并成一个节点。
- `hookBeat` 继续检查前若干拍落地；叙事区段与精确节拍之间的匹配先由内容评审处理，不把五个位置枚举硬换算为等长时段。
- `closure` 表达最终集收束，不要求伪造新的悬念；最终大兑现仍必须有真实节点认领范围。

只认领有效位置不能证明戏剧效果。脚本报告应显示节点 `setup/outcome` 与被认领剧本文本，供人工或当前模型核对。

原有时长估算规则继续使用。前若干拍不等于前 3–5 秒，不把现有 `hookBeat` 门改写成秒级保证。

### 8.2 novel-art：保留数据结构，修正文案与过滤

- 人物、场景、道具编号不变。
- `reusePlan` 有则搬运，无则不制造错误。
- 道具的 `beatIds` 可以指向施压、转折或兑现，界面改称“关联剧情节点”。
- 当前场景 `usage.beats` 是按共同出现集数推算，不证明节点实际发生在该场景。保留时标为“同集关联节点类型”，不能当作精确场景归属。
- 不新增第二份可手动维护的兑现密度统计。
- 不为本次改造强制升级整个 art schema。

### 8.3 novel-characters 与 novel-creation

- 人物 ID、分档、来源字段保持不变，角色 seed 应继续工作。
- creation 继续消费剧本场次与节拍流，不消费大纲的机位方案。
- 检查最终集 `cliff=null` 与新增 `closure` 是否影响现有读取或渲染。
- 多人同框安排在 creation 已有镜头与提示词中处理，不额外新增一套 `crowdPlan` 结构。
- 各 skill 保持自包含，不从兄弟 skill import 新校验器或依赖第三方 skill。

### 8.4 合并报告与管线测试

- 检查 `scripts/report.mjs` 的发现、面板合并、语言切换和交互。
- 更新 `scripts/pipeline-selftest.mjs` 引用的 outline 样例路径。
- 不用单个 skill 的最小上游夹具宣称整条故事管线已经通过。
- 区分“各 skill 自有样例的渲染互操作测试”和“同一故事的跨阶段字段传递测试”。后者使用本轮隔离测试目录，不借用兄弟 skill 样例充当正式示例。

## 9. 报告调整

### 9.1 信息优先级

1. 故事承诺：主角目标、阻力、代价、终局。
2. 节奏总览：每集兑现数、首次大兑现、阶段大兑现位置。
3. 分集叙事：开场、关键事件、状态变化、集尾事件。
4. 悬念对应：提出集、问题、期限、解决集和节点。
5. 内容检查提醒：重复标签、集中结尾、单次场景等。
6. 改编说明、人物、场景、道具和调度矩阵。
7. 结构质量门与明确跳过项。

### 9.2 展示规则

- 时间轴用不同颜色或形状区分施压、转折、兑现，只有兑现显示强度。
- 同一集多个节点按粗略位置和数组顺序排布，不再全部重叠在一个集号坐标上。
- 大纲图表标注“计划位置”，不标伪造的秒数。
- 节奏图显示每集兑现，而不是只显示所有节点总数。
- 最终集显示“终局收束”，不显示“悬念缺失”。
- 结构门使用“通过／失败／跳过”，提示使用“提醒”，内容质量显示“需内容评审”，不可混成一个分数。
- 报告导出的 JSON 与输入数据保持一致，不偷偷写入统计、默认值或评审结论。
- 文本正常转义，防止名称、梗概或问题文本破坏 HTML。
- 中文标签使用完整词语，不使用“保／砍／合”等单字操作标签。

### 9.3 自动汇总接口

`assets` 命令继续只负责资产汇总。`scenes/characters/props/castPlan/warnings` 保持原职责。

原 `beatsByType` 调整为 `nodesByType`，表示全部剧情节点类型；另返回 `payoffsByType`，只包含兑现节点。两者按集号去重并排序，避免同集同类多节点被误读为多个出场集。

新增节奏与悬念视图由渲染器中的纯计算函数获得，不新增手写 JSON 顶层字段，也不新增历史统计文件。

`uses` 继续表示出现集数，不表示镜头数。资产关联数组存在重复 ID 时应拒绝或在计算前规范去重；不能让重复 ID 导致使用集数虚增。

## 10. 版本与迁移策略

### 10.1 明确采用破坏性 v2

- 新生成的大纲和剧本必须声明 `schemaVersion: 2`。
- outline 的 validate/checkup/render/assets，以及 script 的 validate/render/seed，在处理相关主文档时检查支持版本。
- 缺少版本的存量文件视为旧版，不静默套用 v2 语义。
- 未支持版本报清楚的错误及迁移说明路径，不渲染成“全通过”。
- 不建立长期双版本解析层；旧文件仍可由旧提交的工具读取。
- art、characters、creation 对可选上游只消费自身声明的字段，不通过一次成功读取宣称该大纲已经满足 v2 全部质量门。必需字段缺失仍应明确报错。

skill 软件版本建议：outline 与 script 的软件主版本升级到 2.0.0；其他 skill 根据实际接入变化更新版本和日志，不机械统一版本号。

### 10.2 迁移步骤

先备份原文件，再生成新的 v2 草稿，禁止原地盲目转换。

1. 搬运参数、人物、场景、道具和改编取舍。
2. 从原故事重建 `story`；不能只把 `adaptation.core` 改个键名。
3. 审阅旧 `hook`，确定它原本是开场还是集尾问题，再重写 `opening`。
4. 将旧悬念重写为具体事件、问题、期限和编号；最终集改为收束。
5. 逐个审阅旧 beat，判断施压、转折或兑现；将旧 `payoff` 文本作为 `outcome` 草稿，不自动全部标为兑现。
6. 增补缺少的集内兑现和阶段大兑现，填写位置和状态变化。
7. 连接 Q 的解决节点，核对故事因果。
8. 删除旧字段和 `maxBeatGap`，通过完整校验并执行内容评审。
9. 剧本按 B 编号重新认领实际节拍。旧 `beatsClaimed` 的类型名称不能可靠反推多个同类节点，必须重新确认。
10. 重新渲染 Markdown 和 HTML，验证下游 seed。

本轮不新增自动“语义迁移”命令。结构搬运可以通过一次性本地脚本辅助，但分类、兑现和悬念解决不能交给机械字段重命名。

### 10.3 仓库样例处理

- outline 增加自身独立的新故事原文和完整 v2 样例，旧《渡口》不继续作为新版主样例。
- 旧版行为只用最小 inline fixture 测试拒绝与诊断，不保留第二套完整旧版主流程。
- script、art、creation 各自样例和上游夹具只服务本 skill 自己的故事；需要更新字段时在各自目录更新，不跨 skill 引用文件。
- 历史 CHANGELOG 保持历史事实，新增版本说明，不改写为“过去已经有 v2”。

## 11. 新样例设计与验收

先写故事提案，再写原文，再编大纲。故事未确认前不做分镜、不出图。

建议新样例规格：6 集 × 90 秒；独立原创题材；主角通过自己的行动争取权益或完成目标，避免复用旧渡口、皮箱、身份物证的故事骨架。

必须展示：

- 每集至少一次真实兑现。
- 至少一集有两个不同的兑现节点。
- 首次大兑现不晚于第 3 集，最终集有终局大兑现。
- 至少一个施压节点和一个转折节点，证明它们不会被计入兑现。
- 至少一个跨两集解决的悬念，以及一个下一集解决的悬念。
- 至少两个同类节点拥有不同 ID，证明剧本不能按 type 去重认领。
- 至少一个只出现一集、没有 `reusePlan` 的场景仍能通过。
- 至少一集三名以上角色出场，且不需要 `crowdPlan`。
- 最终集 `cliffhanger=null`，主线和情绪承诺都有明确兑现。
- 新样例有自己的原文证据，不能引用其他 skill 的样例文本。

这些是覆盖要求，不先指定具体物件、动作或机位。不得为了测试字段倒推一个缺乏动机的故事。

- `skills/novel-outline/scripts/selftest.mjs`：正例、击穿测试、回归测试。
- `skills/novel-outline/examples/`：新故事原文及 v2 JSON。

### 12.2 下游与仓库说明

- `skills/novel-script/scripts/novel-script.mjs`、`scripts/selftest.mjs`：seed、ID 认领、终局收束及报告。
- `skills/novel-script/SKILL.md`、`references/schema.md`、相关写作指南及自有样例：同步契约。

## 13. 测试计划

### 13.1 schema 与版本

- v2 完整正例通过；缺版本、旧版本、未知未来版本明确拒绝。
- 新旧字段混用拒绝。
- 集号、ID、数组、枚举、有限正整数参数逐项击穿。
- 非兑现节点携带 `weight` 拒绝；兑现缺少强度拒绝。
- 节点位置逆序、引用未知角色/道具/节点拒绝。
- 完全相同前后状态拒绝；不同文本但语义空转留给内容评审，不伪装成自动检测。

### 13.2 节奏与最终集

- 全集只有施压和转折，即使数量很多，也不能通过兑现覆盖。
- 一个场景描述不能仅凭 `type=打脸` 在缺少 `kind=payoff` 时计为兑现。
- 每集最少兑现数边界、显式覆盖值、同集多节点均正确。
- 首次大兑现恰在期限通过，晚一集失败。
- 相邻大兑现差恰等于阈值通过，多一集失败。
- 最终节点错误类型、错误强度、错误集号、未知 ID 均失败。
- 单集、双集、长篇均覆盖。
- 最终集无悬念通过；非最终集无悬念失败。

### 13.3 悬念与阶段

- 默认期限按总集数截断。
- 显式期限合法边界、非法期限均覆盖。
- 同集解决、提前解决、晚于期限、无人解决、重复解决、未知 Q 均失败。
- 一个事件解决多个真实 Q 可以通过。
- 分批草稿中的未来引用不宣称已完整解决；完整阶段必须全部检查。
- arcs 缺省通过；提供后有遗漏、重叠、越界、错误阶段大兑现均失败。

### 13.4 职责回归

- 三名以上角色不再要求 `crowdPlan`。
- 一次性场景无复用方案通过，并出现提示。
- 无 `props` 的合法大纲仍可使用；有 props 时完整检查引用。
- 场景、角色、道具资产汇总的 `uses` 不被重复 ID 增大。
- 制作风险关键词只产生提醒，不制造新的叙事硬门。

### 13.5 script 接口

- opening 正确进入 hook，普通 cliffhanger 正确进入 cliff。
- 最终集进入 closure，不要求伪造 cliff。
- 同类不同 B 节点必须逐个认领。
- 重复、漏领、错集、未知 B、空范围、倒序、越界、重叠范围均失败。
- seed 的 null 范围不能被当成完成剧本。
- 部分集数剧本只要求覆盖自身集数，不误报其他集节点缺失。
- 缺少 outline 时明确跳过跨文档覆盖核对，但本地字段和范围仍检查。
- hookBeat 与原时长估算继续工作。

### 13.6 渲染和管线

- Markdown、HTML、中文、英文界面均覆盖。
- 施压、转折、兑现可区分；同集多节点不重叠丢失。
- 末集收束、未满足期限、骨架跳过项展示准确。
- JSON 导出不改变原始数据。
- 名称、梗概、悬念中的 HTML 特殊字符安全转义。
- 合并报告面板切换、展开、目录发现正常。
- 各 skill 单独拷贝到临时目录后，仍能运行自己的样例与自测，不访问兄弟 skill。
- 浏览器检查报告的窄屏阅读和时间轴；浏览器验收未执行时必须明确标注。

测试不调用真实付费模型。临时文件放隔离目录，结束后仅清理本轮资源，不清理用户历史数据。

## 14. 实施顺序与完成标准

### 阶段 A：冻结契约与故事方向

- 确认 v2 破坏性升级、终局收束、节点分类和默认节奏参数。
- 完成独立样例故事提案，不先做镜头。
- 完成 schema、迁移说明和写作指南草稿。

完成标准：字段只有一个明确含义；每个跨字段关系有可执行判据；不存在未定义的最终集或骨架例外。

### 阶段 B：outline 数据与校验

- 实现版本、字段、分阶段校验。
- 实现节奏与悬念的纯计算逻辑。
- 编写正例和逐门击穿测试。
- 完成新故事原文与大纲的内容评审。

完成标准：新样例完整通过；虚假密度、过晚兑现、未解决悬念均有测试阻断。

### 阶段 C：报告与下游

- 更新 Markdown、HTML、资产汇总命令。
- 同步 script seed、按 ID 认领和 closure。
- 检查 art、characters、creation 接入及合并报告。

完成标准：节点从大纲到剧本有稳定 ID 和实际落点；最终集不再强制新悬念；其他 skill 没有新增跨目录运行依赖。

### 阶段 D：迁移、回归与说明

- 更新各自样例和测试夹具。
- 运行所有受影响自测、管线测试、差异检查和本地链接检查。
- 浏览器检查报告。
- 更新版本和 CHANGELOG。

完成标准：没有仍在宣传旧规则的当前文档；旧数据拒绝时有清楚说明；完整结果区分自动校验、内容评审和未验证的市场效果。

建议按 A、B、C、D 组织可审查的提交，但正式发布必须在所有受影响消费者准备完成后进行，不把中间不兼容状态当作完整交付。

## 15. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 为通过数量门而伪造兑现 | 分类标准、具体结果、状态变化和内容评审共同约束 |
| 每集套同一个结构，剧情机械 | 结构只约束承诺与兑现，不固定事件类型和节点数量 |
| 增加字段导致模型重复劳动 | 删除旧核心、重叠钩子和机位方案；统计保持派生；不重复维护落点列表 |
| 限期解决让长悬疑失去空间 | Q 只表示本集可回答的问题，长期承诺放 story/arcs；显式期限可调整 |
| 旧数据被误当新版 | 显式版本拒绝、人工语义迁移，不自动补假字段 |
| 剧本只是填 ID，没有演出来 | 认领实际节拍范围，报告并排显示上下游文本，内容评审核对 |
| 错把大纲位置当真实时长 | 不在大纲显示秒数；实际节奏留到剧本和成片验证 |
| 内容评审被报告包装成硬保证 | 渲染器只展示结构事实，不自行写“故事精彩”或“爆款概率” |

## 16. 方法来源与验证限制

本方案的字段和接口依据当前仓库实现。节奏数值属于建议的初始创作策略，没有通过本仓库真实投放实验验证。

外部参考：TikTok for Business 的 [Creative Best Practices for TikTok Ads](https://ads.tiktok.com/business/en/blog/creative-best-practices-top-performing-ads) 强调尽早吸引注意。该材料针对广告，只作为开场注意力设计的参考，不能证明短剧的最佳兑现频率，更不能证明爆款概率。

实施时，将本方案中的分类、因果、兑现和评审规则内化到 outline 自己的 references 文档并注明学习来源。运行 skill 不需要联网阅读上述材料，不依赖第三方 skill。

市场效果仍需在真实作品发布后验证留存、完播和追更表现。本轮不新增埋点、报表系统或失败累积统计。
